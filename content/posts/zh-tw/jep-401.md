## 概要

引入*值物件（value object）*。值物件是不可變的，並且沒有物件身份（object identity）。值物件完全由其欄位值來區分，因此 Java 虛擬機可以採用有助於提升性能的方式來表示它們。這是一項[預覽語言和 VM 特性](https://openjdk.org/jeps/12)。

## 目標

- 讓開發者可以選擇一種面向不可變資料的程式模型；在這種模型中，`==` 運算符以及其他所有操作都依據物件欄位的值，而不是物件身份來區分物件。

- 支援將現有的不可變資料類以相容方式遷移到這一模型。將 Java 平台 API 中適合的現有類（例如 `Integer` 和 `LocalDate`）遷移為其實例屬於值物件的類。

- 不要求開發者學習新的記憶體管理或變數儲存語義。Java 語言仍然只處理兩類資料：基本類型值和物件引用。

- 盡可能擴大 JVM 實現者的自由度，使其能夠用有助於改善記憶體占用、局部性和垃圾回收效率的方式表示不可變資料。

## 非目標

- 本提案不以自動將現有類的實例視為值物件為目標。值物件並非在所有方面都與其他物件採用相同的工作方式，因此類的作者必須顯式選擇讓該類的實例成為值物件。

- 本提案不以修改 `==` 運算符、使其能夠替代 `equals` 方法為目標。我們只會在適應這種新的、無身份物件所必需的範圍內重新定義 `==`。在大多數場景中比較物件時應使用 `equals` 方法，這一慣常建議仍然適用。

- 本提案不以引入類似 [C](<https://en.wikipedia.org/wiki/Struct_(C_programming_language)>) 和 [C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/struct) 中的 `struct` 特性為目標。

- 本提案不以改變基本類型的處理方式為目標。基本類型在許多方面的行為與值物件相似，但兩者仍是不同的概念。

- 本提案不保證任何特定的最佳化策略或記憶體布局。本提案使許多最佳化成為可能，但初期只會實現其中一部分。某些最佳化（例如不為 `null` 預留表示空間的布局）要等到未來的語言和 JVM 增強之後才可能實現。

## 動機

很多簡單的資料值都是不可變的，例如複數、像素顏色、時間、日期等。我們通常使用類來建模這類值：類中只包含構造、校驗和轉換實例所需的邏輯，並定義 `equals`、`hashCode` 和 `toString` 方法，使等價的實例可以互換使用。

例如，平台 API 中的 [`LocalDate`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/time/LocalDate.html) 類用於表示日期：

```text
jshell> LocalDate d1 = LocalDate.of(1996, 1, 23)
d1 ==> 1996-01-23

jshell> LocalDate d2 = d1.plusYears(30)
d2 ==> 2026-01-23

jshell> LocalDate d3 = d2.minusYears(30)
d3 ==> 1996-01-23

jshell> d1.equals(d3)
$4 ==> true
```

直觀地說，一個 `LocalDate` 物件的本質在於它的年、月、日三個值。但在 Java 語言中，任何物件的本質都包括它的*身份（identity）*。每當 `LocalDate.of` 方法呼叫 `new LocalDate(...)` 時，JVM 都會建立一個具有唯一身份的新物件，使它能夠與系統中的其他所有物件區分開來。

觀察物件身份最簡單的方式，就是使用 `==` 運算符：

```text
jshell> d1 == d3
$6 ==> false
```

儘管 `d1` 和 `d3` 表示同一個「年-月-日」三元組——也就是說，`d1.equals(d3)` 為 `true`——它們仍然是兩個身份不同的物件。

### 不可變資料不需要身份

對於可變物件來說，身份非常重要：它讓我們能夠區分兩個目前狀態相同、但未來狀態可能不同的物件。假設有一個文字編輯應用，其中每一行文字都由 `Line` 類的實例表示。該類唯一的欄位是一個字元列表，使用者編輯這一行時就會修改這個列表。兩個 `Line` 物件可能包含內容相同的字元列表，因此目前看起來也是等價的，但這只是偶然；當使用者修改其中一行時，應用會修改對應物件中的字元列表，而不會修改另一個物件，它依靠物件身份來確保改動落在正確的物件上。

換句話說，可變物件不能彼此互換；而大多數不可變資料值都可以互換。兩個都表示 `1996-01-23` 的 `LocalDate` 物件之間沒有實際差別，因為它們的狀態固定不變。無論現在還是將來，它們都表示同一個值，因此沒有必要透過身份來區分這兩個物件。

事實上，當物件既不可變又可互換時，物件身份反而容易造成困惑。很多人都經歷過不小心使用 `==` 比較物件——例如上面的 `d1 == d3`——結果明明物件的狀態和行為看起來完全相同，卻得到了 `false`，讓人摸不著頭腦。

更糟的是，物件身份還可能暴露原本只是實現細節的選擇，從而產生令人意外的行為。例如，`Integer` 類會使用一個[快取](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/Integer.html#valueOf(int)>)，以避免建立不必要的、具有唯一身份的 `Integer` 物件。比如，通常只會有一個表示數值 `1` 的 `Integer` 物件。但快取大小是固定的，並不會覆蓋像 `1996` 這樣更大的 `int` 值：

```text
jshell> Integer i = 1, j = 1;
i ==> 1
j ==> 1

jshell> i == j
$3 ==> true

jshell> Integer x = 1996, y = 1996;
x ==> 1996
y ==> 1996

jshell> x == y
$6 ==> false
```

如果那些從狀態和行為上看已經可以彼此互換的物件，不再受「必須擁有不同身份」這一傳統要求的約束，我們就可以避免這類意外結果。

### 物件身份在執行時是有成本的

Java 語言要求每個物件都具有身份，無論這個身份是否真的需要，這會成為性能上的負擔。JVM 因而必須為每個新建立的物件分配記憶體，使它能夠與系統中已經存在的所有其他物件區分開來；而每次使用物件時，又都需要訪問相應的記憶體。

例如，假設程式建立了 `int` 值陣列和 `LocalDate` 引用陣列：

```text
jshell> int[] ints = { 1996, 2006, 1996, 1, 23 }
ints ==> int[5] { 1996, 2006, 1996, 1, 23 }

jshell> LocalDate[] dates = { d1, d1, d2, null, d3 }
dates ==> LocalDate[5] { 1996-01-23, 1996-01-23, 2026-01-23,
                         null, 1996-01-23 }
```

`int` 陣列可以表示成一塊連續的記憶體，其中直接儲存 `int` 值：

```text
+----------+
| int[5]   |
+----------+
| 1996     |
| 2006     |
| 1996     |
| 1        |
| 23       |
+----------+
```

相比之下，`LocalDate` 陣列必須表示為一塊存放一系列指標的記憶體；每個指標再指向另一塊表示 `LocalDate` 物件的記憶體：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 87fa1a09     | -----------------------> +-----------+
| 87fa1a09     | -----------------------> | LocalDate |
| 87fb4ad2     | ------> +-----------+    +-----------+
| 00000000     |         | LocalDate |    | y=1996    |
| 87fb5366     | ---     +-----------+    | m=1       |
+--------------+   |     | y=2026    |    | d=23      |
                   v     | m=1       |    +-----------+
        +-----------+    | d=23      |
        | LocalDate |    +-----------+
        +-----------+
        | y=1996    |
        | m=1       |
        | d=23      |
        +-----------+
```

儘管 `LocalDate` 陣列所表示的資料並不比 `int` 陣列複雜多少——一個「年-月-日」三元組本質上只是 48 位基本類型資料——但因為存在指標和單獨分配的物件，它的記憶體占用要大得多。

更糟的是，當程式遍歷 `LocalDate` 陣列時，可能需要逐一解引用這些指標。現代 CPU 會透過快取稱為[快取行（cache line）](https://en.wikipedia.org/wiki/CPU_cache#CACHE-LINES)的小塊記憶體來提升性能。如果各個 `LocalDate` 物件是在不同時間建立的，或者後來被垃圾收集器移動過，那麼它們在記憶體中的地址可能相距很遠。由此造成較差的[引用局部性](https://en.wikipedia.org/wiki/Locality_of_reference)，可能使每次解引用都不得不從記憶體載入不同的快取行，從而降低性能。

走投無路時，我們可能會嘗試通過盡量少建立物件來提高性能，以減輕垃圾收集器的壓力並改善引用局部性。例如，與其使用 `LocalDate` 物件，我們可以用 `int` 值來表示日期，讓它記錄[自 1970-01-01 起經過的天數](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/time/chrono/ChronoLocalDate.html#toEpochDay()>)。遺憾的是，這樣做會放棄類所提供的、讓 Java 程式碼易於維護的許多能力：有意義的名稱、私有狀態、構造器中的資料校驗、便捷方法等等。開發者很容易忘記——或者同事根本不知道——這些表示日期的 `int` 是以 1970-01-01 而不是其他某個日期為基準，從而引入難以診斷的錯誤。

### 在沒有身份的情況下編程

每天都會建立數以萬億計的 Java 物件，每一個都帶著唯一身份。我們應該讓開發者決定：程式中的哪些物件需要身份，哪些不需要。像 `LocalDate` 這樣表示簡單不可變資料的類，其作者應該能夠選擇放棄身份。兩個都表示日期 `1996-01-23` 的 `LocalDate` 物件應該不可區分，就像兩個都表示數字 `4` 的 `int` 值不可區分一樣。

選擇放棄身份，也就等於選擇了一種兼得兩方面優點的程式模型：既保留類所提供的抽象能力，又獲得基本類型的簡潔性和性能優勢。

未來，這一編程模型還將支援新的 Java 平台 API，例如表示不同整數和浮點數形式的類，以及新的 Java 語言特性，例如面向不可變資料的使用者自訂轉換和數學運算符。

## 描述

我們引入*值物件（value object）*來表示簡單的不可變資料。值物件是*值類（value class）*的實例；值類使用 `value` 修飾符宣告。沒有 `value` 修飾符的類稱為*身份類（identity class）*，其實例稱為*身份物件（identity object）*。

Java 程式透過*引用（reference）*操作物件。物件引用儲存在變數中，使我們能夠找到物件的欄位。傳統上，在 JVM 中，引用表示為指向記憶體位置的指標，因此也編碼了每個物件的唯一身份。每次呼叫 `new` 運算符，都會在一塊新的記憶體中分配一個全新物件並返回一個唯一引用。傳統上，`==` 運算符透過比較指標來比較引用，所以即使兩個被引用的物件可以互換，只要它們是兩個不同物件，對應的引用也不會滿足 `==`。

值物件則不同。值物件的引用同樣儲存在變數中，並使我們能夠找到物件的欄位；但在 JVM 中，它不一定用指標表示，因此也不一定編碼物件的唯一身份。對於值類，呼叫 `new` 運算符未必真的分配一個新物件；它可能返回一個已經存在的物件的引用，甚至可能返回一個直接承載物件內容的引用。`==` 運算符比較值物件引用時，會比較物件的欄位值，因此如果兩個物件擁有完全相同的欄位值，對應的引用就滿足 `==`。

對不可變資料使用值物件，可以節省記憶體並提升性能。由於程式無法區分兩個欄位值完全相同的值物件——即使使用 `==` 運算符也不行——JVM 就可以在不影響程式行為的前提下改變值物件的記憶體布局。例如，JVM 可以把值物件的欄位儲存在堆疊上，甚至直接儲存在 CPU 暫存器裡，而不是放在堆上。

### 值物件是一項預設關閉的[預覽語言和 VM 特性](https://openjdk.org/jeps/12)

要在 JDK 28 中使用這一特性，必須啟用預覽特性：

- 使用 `javac --release 28 --enable-preview Main.java` 編譯程式，並使用 `java --enable-preview Main` 執行；或者，

- 使用[原始碼啟動器](https://openjdk.org/jeps/330)時，通過 `java --enable-preview Main.java` 執行程式；或者，

- 使用 [jshell](https://openjdk.org/jeps/222) 時，通過 `jshell --enable-preview` 啟動。

Java 平台 API 中的[某些類](#java-平台中的值類)只有在啟用預覽特性時才會成為值類；否則，它們的行為與 JDK 27 中完全相同。

例如，如果程式碼引用了 `LocalDate` 類，而編譯時沒有啟用預覽特性，那麼編譯器會使用現有的身份物件版本 `LocalDate`，執行程式時也無需啟用預覽特性。但如果編譯時啟用了預覽特性，編譯器就會使用新的值物件版本 `LocalDate`，執行程式時也必須啟用預覽特性。啟用預覽特性後，無法再使用 `LocalDate` 的身份物件版本。

### 使用值物件進行編程

Java 平台 API 中現在有 30 個類被宣告為值類，例如：

| 包        | 類                                                                            |
| --------- | ----------------------------------------------------------------------------- |
| java.lang | `Integer`, `Long`, `Float`, `Double`, `Byte`, `Short`, `Character`, `Boolean` |
| java.util | `Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`                   |
| java.time | `LocalDate`, `LocalTime`, `LocalDateTime`, `ZonedDateTime`, `Duration`        |

這些類的所有實例都是值物件。其中包括作為 `Integer`、`Long` 等類實例的[裝箱基本類型值](https://download.java.net/java/early_access/jdk28/docs/specs/jls/jls-5.html#jls-5.1.7)。`==` 運算符按欄位值比較值物件，因此，例如，如果兩個 `Integer` 物件表示同一個基本類型值，它們就滿足 `==`：

```text
$ jshell --enable-preview
|  Welcome to JShell -- Version 28-internal
|  For an introduction type: /help intro

jshell> Integer x = 1996, y = 1996;
x ==> 1996
y ==> 1996

jshell> x == y
$3 ==> true
```

同樣，只要兩個 `LocalDate` 物件擁有相同的年、月、日值，它們就滿足 `==`：

```text
jshell> LocalDate d1 = LocalDate.of(1996, 1, 23)
d1 ==> 1996-01-23

jshell> LocalDate d2 = d1.plusYears(30)
d2 ==> 2026-01-23

jshell> LocalDate d3 = d2.minusYears(30)
d3 ==> 1996-01-23

jshell> d1 == d3
$7 ==> true
```

可以使用新的 `Objects.hasIdentity` 方法來觀察某個物件是否為身份物件：

```text
jshell> Objects.hasIdentity(d1)
$8 ==> false
```

由於 `String` 類的 API 和實現中存在一些對物件身份的依賴，因此它不是值類，所以 `String` 的實例始終是身份物件：

```text
jshell> String s = "abcd"
s ==> "abcd"

jshell> Objects.hasIdentity(s)
$10 ==> true

jshell> String t = "aabcd".substring(1)
t ==> "abcd"

jshell> s == t
$12 ==> false
```

在大多數方面，值物件與 Java 語言中一貫的物件工作方式相同：它們有欄位和方法，透過引用來操作，而且引用可以為 `null`。

不過，值物件不支援少數依賴身份的操作，其中包括同步：

```text
jshell> synchronized (d1) { d1.notify(); }
|  Error:
|  unexpected type
|    required: a type with identity
|    found:    java.time.LocalDate
|  synchronized (d1) { d1.notify(); }
|  ^--------------------------------^

jshell> Object o = d1
o ==> 1996-01-23

jshell> synchronized (o) { o.notify(); }
|  Exception java.lang.IdentityException: Cannot synchronize on
   an instance of value class java.time.LocalDate
|        at (#19:1)
```

JVM 實現者可以自由決定值物件引用在執行時的編碼方式，以最佳化記憶體占用、局部性和垃圾回收效率。例如，前文曾看到下面這個透過指標指向堆物件實現的陣列：

```text
jshell> LocalDate[] dates = { d1, d1, d2, null, d3 }
dates ==> LocalDate[5] { 1996-01-23, 1996-01-23, 2026-01-23,
                         null, 1996-01-23 }
```

現在，由於 `LocalDate` 物件沒有身份，JVM 不必再使用指標表示它們的引用，而可以把 `LocalDate` 物件的欄位直接編碼進引用。`dates` 陣列中的每個元素都可以表示為一個 64 位字：它先表示引用是否為 `null`；如果不是 `null`，就直接儲存值物件的年、月、日欄位值：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 1|1996|01|23 |
| 1|1996|01|23 |
| 1|2026|01|23 |
| 0|0000|00|00 |
| 1|1996|01|23 |
+--------------+
```

這種 `LocalDate` 陣列的效能特徵可能與普通 `int` 陣列類似，同時擁有更低的記憶體占用和更好的引用局部性：

```text
+----------+
| int[5]   |
+----------+
| 1996     |
| 2006     |
| 1996     |
| 1        |
| 23       |
+----------+
```

這只是一種可能的最佳化方式；有些值類（例如 `LocalDateTime`）太大，無法利用這種具體技術。不過，沒有身份這一點仍然讓 JVM 實現者能夠以多種方式最佳化值物件引用。

### 宣告值類

可以在任何其實例應當保持不可變並且可互換的類上使用 `value` 修飾符，從而宣告自己的值類：

- _不可變（Immutable）_——類的所有實例欄位都是 `final`，而且一個實例所表示的值不會隨時間發生變化；以及

- _可互換（Interchangeable）_——沒有必要區分兩個分別建立、但表示相同值的實例。

當類使用 `value` 修飾符時，其欄位會隱式成為 `final`。類本身也會隱式成為 `final`，因此不能被繼承。由於類是 `final`，它的方法也不能被覆蓋。

值類中的欄位類型沒有限制。欄位既可以儲存對其他值物件的引用，也可以儲存對身份物件（例如字串）的引用。

[Record 類](https://openjdk.org/jeps/395)本身是 `final` 的，而且它們的所有欄位也是 `final`，因此通常很適合成為值類：

```text
jshell> value record Point(int x, int y) {}
|  created record Point

jshell> Point p = new Point(17, 3)
p ==> Point[x=17, y=3]

jshell> Objects.hasIdentity(p)
$3 ==> false

jshell> new Point(17, 3) == p
$4 ==> true
```

很多類的實例同樣既不可變又可以互換，但它們不能宣告為 record，因為其欄位並不與構造器參數完全對應；也就是說，它們並不*透明（transparent）*。這類物件可能在內部使用私有欄位，以一種比公開方法所暴露的表示方式更高效的方式儲存資料。例如，一個類可以為了節省記憶體，用一個 `long` 欄位統一表示歐元和歐分；它不能成為 value record，但仍然可以成為值類：

```java
value class EURCurrency {

    private long cs;  // implicitly final

    private EURCurrency(long cs) { this.cs = cs; }

    public EURCurrency(long e, int c, boolean neg) {
        this(neg ? -e * 100 - c : e * 100 + c);
    }

    public EURCurrency(long e, int c) { this(e, c, false); }

    public long euros() { return Math.abs(cs) / 100; }
    public int cents() { return (int) Math.abs(cs) % 100; }
    public boolean negative() { return cs < 0; }

    public String toString() {
        var prefix = negative() ? "-€" : "€";
        return "%s%d,%d".formatted(prefix, euros(), cents());
    }

}
```

### 比較值物件

傳統上，`==` 運算符的用途是判斷兩個被引用的物件是否具有相同的身份。

引入值物件後，`==` 運算符的用途變成判斷兩個被引用的物件是否不可區分。由於身份物件按定義就是透過身份來區分的，因此對於身份物件，Java 28 中的 `==` 與從 Java 1.0 開始一直以來的行為完全相同：它判斷兩個引用是否指向同一個物件——也就是同一個記憶體位置——或者判斷兩個引用是否都是 `null`。

比較兩個值物件時，`==` 運算符會檢查它們是否引用同一個類、並且欄位值相同的實例。也就是說，兩個值物件在以下條件都成立時不可區分：

- 它們是同一個值類的實例；

- 它們的基本類型欄位儲存相同的位模式；以及

- 它們的引用類型欄位彼此不可區分，也就是遞迴地對這些欄位應用 `==` 運算符。

滿足這些條件時，JVM 就可以自由地用一個引用取代另一個，而任何程式碼都無法察覺差別。

對於值物件，`==` 運算符和 `equals` 方法通常會得到相同的結果。不過，對於某些值類，即使實例的欄位值不同（也就是不滿足 `==`），它們仍然可能是可互換的（也就是 `equals` 為 `true`）。**要判斷兩個值物件是否表示同一個值，應使用 `equals` 方法。宣告類時，應當以這樣一種方式定義 `equals`：對於可互換的實例，它始終返回 `true`。**

下面的 `Substring` 值類說明了某些值物件中 `==` 和 `equals` 可能產生不同結果的情況。這個類表示字串的一個子串，但不會在記憶體中重新分配一個新的 `char[]`。一個 `Substring` 實例的內部狀態由源字串和兩個位置坐標組成，而該實例所表示的值則是 `toString` 產生的字元序列。因此，兩個實例可能表示相同的字元序列（也就是 `equals` 為 `true`），但內部狀態不同（也就是不滿足 `==`）。

```java
value class Substring {

    private String str;
    private int start, end;

    public Substring(String s, int i, int j) {
        str = s; start = i; end = j;
    }

    public String toString() {
        return str.substring(start, end);
    }

    public boolean equals(Object o) {
        return o instanceof Substring && toString().equals(o.toString());
    }

    public int hashCode() {
        return Objects.hash(Substring.class, toString());
    }

}

jshell> Substring sub1 = new Substring("ringing", 1, 4);
sub1 ==> ing

jshell> Substring sub2 = new Substring("ringing", 4, 7);
sub2 ==> ing

jshell> sub1.equals(sub2)
$3 ==> true

jshell> sub1 == sub2
$4 ==> false
```

如果兩個值物件的欄位分別引用兩個不同的身份物件，而這兩個身份物件根據 `equals` 判斷又是可互換的，那麼 `==` 與 `equals` 的結果同樣可能不同：

```text
jshell> String r = "bringing".substring(1);
r ==> ringing

jshell> r == "ringing"
$6 ==> false

jshell> Substring sub3 = new Substring(r, 1, 4);
sub3 ==> ing

jshell> sub1.equals(sub3)
$8 ==> true

jshell> sub1 == sub3  // tests sub1.str == sub3.str
$9 ==> false
```

值物件包含 `float` 或 `double` 欄位時，也是 `==` 與 `equals` 可能不同的另一種情況。基本浮點類型支援多個不同的 `NaN` 值。大多數浮點運算會把這些 `NaN` 視為可互換，但由於每個值仍然不同，封裝不同 `NaN` 值的值物件可以被 `==` 運算符區分出來。宣告值類時，必須自行決定這種區別對於 `equals` 方法是否有意義。例如，在 value record 中，`equals` 的預設行為會把所有 `NaN` 值都視為可互換：

```text
jshell> value record Length(float val) {}
|  created record Length

jshell> Length l1 = new Length(Float.intBitsToFloat(0x7ff80000))
l1 ==> Length[val=NaN]

jshell> Length l2 = new Length(Float.intBitsToFloat(0x7ff80001))
l2 ==> Length[val=NaN]

jshell> l1.equals(l2)
$4 ==> true

jshell> l1 == l2
$5 ==> false

jshell> Integer.toHexString(Float.floatToRawIntBits(l1.val()))
$6 ==> "0x7ff80000"

jshell> Integer.toHexString(Float.floatToRawIntBits(l2.val()))
$7 ==> "0x7ff80001"
```

（關於浮點值之間不同形式的等價關係，詳見 [`Double` 類的規範](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/Double.html#fpNumericalEq)。）

由於 `==` 運算符會遞迴比較值物件中的引用類型欄位，因此比較兩個值物件時，所需的比較次數可能沒有固定上限。下面的範例中，為了判斷兩個深層嵌套的 `Box` 物件是否不可區分，必須完整遍歷整個嵌套結構：

```text
jshell> value record Box(Object val) {}
|  created record Box

jshell> var b1 = new Box(new Box(new Box(new Box(l1))))
b1 ==> Box[val=Box[val=Box[val=Box[val=Length[val=NaN]]]]]

jshell> var b2 = new Box(new Box(new Box(new Box(l2))))
b2 ==> Box[val=Box[val=Box[val=Box[val=Length[val=NaN]]]]]

jshell> b1.equals(b2)
$11 ==> true

jshell> b1 == b2
$12 ==> false
```

如[下文](#值物件的安全構造)所述，值類構造器會受到一定約束，因此遞迴地對值物件應用 `==` 運算符絕不會造成無限循環。不過，深度比較仍然可能耗費很長時間，甚至觸發 `StackOverflowError`。

### 值類與子類化

與每個身份類一樣，每個值類也都屬於一個以 `java.lang.Object` 為根的類層次結構。不存在一個作為所有值類共同父類的 `java.lang.Value`。

值類可以實現介面。因此，宣告為介面類型或 `Object` 類型的變數，可以同時儲存值物件和身份物件的引用：

```text
jshell> Comparable<?> comp = LocalDate.of(1996, 1, 23)
comp ==> 1996-01-23

jshell> Objects.hasIdentity(comp)
$2 ==> false

jshell> comp = "abc"
comp ==> "abc"

jshell> Objects.hasIdentity(comp)
$4 ==> true
```

預設情況下，值類隱式為 `final`，不能被繼承。不過，值類也可以宣告為 `abstract`，從而允許其他類繼承它，並允許其方法被覆蓋。抽象值類的欄位與具體值類一樣，也隱式為 `final`。抽象值類的方法則可以像抽象身份類一樣標記為 `abstract`。

將一個類宣告為抽象值類，表示該類本身不需要身份。它的子類既可以是值類，也可以是身份類。（抽象值類上的 `value` 修飾符也可以理解為表示*值相容（value-compatible）*。）

值類可以繼承 `java.lang.Object` 或抽象值類，但不能繼承身份類。（`Object` 在這一點上很特殊：它既不是抽象類，也不是值類，而且 `new Object()` 建立的實例具有身份，但它仍然允許值類繼承。）

許多現有的抽象類，如果本來就是為公開擴展而設計的，那麼很適合成為抽象值類。例如，抽象類 `Number` 沒有欄位，也沒有任何依賴身份敏感特性的程式碼，因此可以安全地遷移為抽象值類：

```java
abstract value class Number implements Serializable {
    public abstract int intValue();
    public abstract long longValue();
    public byte byteValue() { return (byte) intValue(); }
    ...
}
```

值類 `Integer` 和身份類 `java.math.BigInteger` 都繼承 `Number`：

```text
jshell> Number num = 123
num ==> 123

jshell> Objects.hasIdentity(num)
$2 ==> false

jshell> num = BigInteger.valueOf(123)
num ==> 123

jshell> Objects.hasIdentity(num)
$4 ==> true
```

抽象值類也可以使用 [`sealed`](https://openjdk.org/jeps/409) 來限制哪些類可以繼承它：

```java
sealed abstract value class UserID
    permits EmailID, PhoneID, UsernameID
{
    ...
}

value class EmailID extends UserID {
    private String name, domain; ...
}

value class PhoneID extends UserID {
    private String digits; ...
}

value class UsernameID extends UserID {
    private String name; ...
}
```

### 值物件的安全構造

構造器透過設定欄位值來初始化新建立的物件。由於值物件沒有身份，其他程式碼只能在它們的欄位值全部初始化完成之後觀察到它們。

為了保證這一點，值物件的欄位必須在物件被共享給其他程式碼之前完成賦值。這也會阻止兩個值物件直接或間接地互相引用，從而確保呼叫 `==` 運算符時絕不會出現無限循環。

一個仍處於構造過程中的物件稱為*幼體（larval）*物件：它已經被建立，但還沒有完全成形。處理幼體物件時始終需要格外謹慎。如果幼體物件在構造器中被洩露給構造器之外的程式碼，那麼物件的不變數可能尚未成立，而且外部程式碼甚至可能觀察到 `final` 欄位被修改的過程。

傳統上，構造器透過呼叫超類構造器 `super(...)` 開始初始化。如果構造器沒有顯式這樣做，Java 編譯器就會在構造器主體開頭插入一次 `super()` 呼叫。超類構造器返回之後，子類構造器才會繼續設定自己宣告的實例欄位，並執行其他初始化工作。這種模式意味著，在任意超類構造器執行期間，一個子類欄位完全尚未初始化的物件都有可能被洩露出去。

Java 25 引入的[靈活構造器主體（Flexible Constructor Bodies）](https://openjdk.org/jeps/513)提供了更安全的初始化機制，允許在呼叫 `super(...)` 之前先設定欄位或執行其他程式碼。借助這一特性，物件初始化分成兩個階段：呼叫 `super(...)` 之前的*早期構造（early construction）*，以及呼叫之後的*後期構造（late construction）*。

在早期構造階段，幼體物件不可能被洩露。構造器可以設定幼體物件的欄位，但不能呼叫實例方法，也不能以其他方式使用 `this`。因此，在早期構造階段完成初始化的欄位一定會先被設定，之後才可能被讀取，即使某個超類後來洩露了幼體物件也是如此。特別是，外界永遠無法觀察到 `final` 欄位被修改。

在值類中，構造器程式碼始終執行在早期構造階段。Java 編譯器會把 `super()` 呼叫插到構造器主體末尾，而不是開頭。嘗試呼叫實例方法或以其他方式使用 `this` 都會失敗：

```java
value class Name {

    String name;
    int length;

    private int strLength() {
        return name.length();
    }

    Name(String n) {
        name = n;
        length = strLength();  // Error, invokes this.strLength()
    }

}
```

帶初始化表達式的實例欄位會在構造器開始執行時、也就是早期構造階段完成設定。實例初始化塊是一項很少使用的特性，它們會在後期構造階段執行；值類的實例初始化塊不允許設定實例欄位。

如果值類構造器中的某些程式碼確實需要使用 `this`，可以顯式呼叫 `super(...)` 或 `this(...)`，以此標記從早期構造階段切換到後期構造階段。不過，在呼叫 `super(...)` 之前，必須在不引用 `this` 的情況下為該類的所有欄位完成賦值：

```java
value class Name {

    String name;
    int length;

    private static int strLength(String n) {
        return n.length();
    }

    Name(String n) {
        name = n;
        length = strLength(name);  // OK, strLength is now static
        super();                   // All fields must be set at this point
        System.out.println("Name: " + this);
    }

}
```

### 其他構造增強

我們放寬了對所有幼體物件欄位訪問的一些限制，無論這些物件是值物件還是身份物件。在 Java 27 中，新物件的欄位可以在早期構造階段寫入，但不能讀取。在 Java 28 中，啟用預覽特性後，這些欄位在早期構造階段既可以寫入，也可以讀取。不過，在進入後期構造階段之前，引用繼承而來的欄位、呼叫實例方法，或者把 `this` 共享給其他程式碼仍然是非法的。

此外，為了簡化模型並提升性能，在 Java 28 中啟用預覽特性後，所有 record 類——無論是 value record 還是 identity record——都會採用與值類相同的安全構造規則。record 類的構造器始終執行在早期構造階段。record 的欄位必須在能夠被觀察之前完成設定，因此類的使用者始終可以預期對 component 的訪問會得到一致的結果。

對於 identity record 的構造器宣告而言，這一修改不具備原始碼相容性，不過我們預計實際出現不相容的情況會很少。例如，下面這個 record 類無法編譯，因為它的規範構造器在早期構造階段引用了 `this`：

```java
record Node(String label, List<Node> edges) {

    static void nullCheck(Object arg, Object owner) {
        if (arg == null) {
            String msg = "null arg for " + owner.toString();
            throw new IllegalArgumentException(msg);
        }
    }

   public Node {
        nullCheck(label, this);  // Error with --enable-preview
        nullCheck(edges, this);  // Error with --enable-preview
    }

}
```

這類不相容情況之所以會很少，是因為如上例所示，在 record 構造器中嘗試使用 `this` 往往本身就是一個 bug：當這裡的程式碼呼叫 `toString()` 時，`Node` 的欄位甚至還沒有完成設定。對大型原始碼語料庫中現有 record 類宣告的調查也證實，record 類違反這些新規則的情況很少見。

如果 record 構造器確實必須訪問 `this`，可以插入顯式的 `super()` 呼叫，但在此之前必須先在早期構造階段顯式設定 record 的欄位。

### 繼承自 `java.lang.Object` 的方法

與任何類一樣，值類也會繼承 `java.lang.Object` 中的 `equals`、`hashCode` 和 `toString` 等方法，除非類自身覆蓋了它們。這些方法傳統上依賴物件身份；但當它們作用於值物件時，會改用物件欄位的值。具體來說：

- 繼承自 `Object.equals` 的實現會使用 `==` 運算符判斷物件是否不可區分。[對於值類來說，這可能正是合適的 `equals` 行為](#比較值物件)；如果不是，類就應該覆蓋 `equals` 方法。

- 繼承自 `Object.hashCode` 的實現會根據物件欄位的值計算雜湊值。（也可以透過 `System.identityHashCode` 計算出這個值——這是一個頗為遺憾的歷史遺留名稱。）與通常規則一樣，如果值類覆蓋了 `equals`，也應同時覆蓋 `hashCode`。

- 繼承自 `Object.toString` 的實現會返回形如 `"ClassName@hashCode"` 的字串。由於值類表示不可變資料，因此應該覆蓋 `toString`，以更清晰地表達實例所表示的值。

在 value record 中，與所有 record 一樣，`equals`、`hashCode` 和 `toString` 的預設行為會遞迴地將相同的操作應用到 record 的各個 component 上。

`Object` 中還有少數其他方法會與值物件發生互動：

- 對於實現了 `Cloneable` 的值類，`Object.clone` 方法會產生一個與原物件不可區分的值物件。對於值物件來說，通常所說的 `x.clone() != x` 並沒有意義。宣告一個儲存身份物件引用的值類時，可以考慮覆蓋 `clone` 方法，為這些物件建立深複製。

- `wait` 和 `notify` 方法要求物件已經被目前執行緒鎖定。由於無法在值物件上進行同步，因此嘗試呼叫這些方法時總會以 `IllegalMonitorStateException` 失敗。

- 值物件的 `finalize` 方法永遠不會被垃圾收集器呼叫。對於覆蓋了 `finalize` 的值類，`javac` 會產生 `identity` 警告。

### 遷移到值類

對於任何用於表示簡單不可變資料的類而言，值類和 record 都是非常有用的工具。

一般來說，如果一個狀態不可變的類並不需要身份，那麼它很可能適合使用 `value` 修飾符。這也包括抽象類：抽象類通常根本沒有狀態，因此不應該無謂地把「必須具有身份」的要求強加給它的子類。（當然，也有一些抽象類雖然沒有宣告可變狀態，但定義了本質上屬於可變模型的 API，因此不應該成為值類；還有一些具體類根本不是用來表示資料的，例如它們可能被設計成只實例化一次。）

如果一個類本身是 `final` 或 `abstract`，而且只包含 `final` 欄位，那麼添加或移除 `value` 關鍵字屬於二進制相容的修改。

不過，將身份類遷移成值類仍然存在一些值得考慮的原始碼和行為相容性風險：

- 如果類具有公開構造器，現有用戶端可能依賴這些構造器建立能夠透過 `==` 與其他所有物件區分開的物件。把這個類改成值類後，這種邏輯就不再成立，並可能導致執行時 bug。

  如果這種不相容風險比較嚴重，可以考慮棄用公開構造器，並鼓勵使用工廠方法。例如，Java 9 中就棄用了 `Integer`、`Long` 等類的構造器，並建議改用相應的 `Integer.valueOf`、`Long.valueOf` 等工廠方法。

- 如果現有用戶端會在該類實例上進行同步，那麼遷移之後，這些程式碼會失敗：要嘛在編譯期報錯，要嘛在執行時拋出 `IdentityException`。對於具有公開構造器的類，這種風險更值得關注，因為用戶端可能依賴構造器建立唯一實例，並把它們用作鎖。

- 如果 `equals` 和 `hashCode` 方法原先沒有被覆蓋，那麼遷移之後它們的行為會發生變化。一個合適的遷移候選類，應當在遷移前就已經覆蓋這些方法，使其行為不依賴物件身份。

- 如果類封裝了敏感資料，需要注意透過 `==` 運算符或 `System.identityHashCode` 暴露這些資料的風險。惡意使用者可能嘗試利用這些操作推斷實例內部的資料。值物件並不是為抵禦這類針對敏感資料的攻擊而設計的。

- 如果類實現了 `Serializable`，則可能需要特殊處理，具體參見[下文](#serialization)。此外，將其遷移為值類還可能破壞反射和垃圾回收 API 的某些用法，具體參見[下文](#reflection)，也可能影響其他依賴物件身份的專用程式碼。

### Java 平台中的值類

Java 平台 API 中現在有 30 個類被宣告為值類：

| 包                 | 類                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `java.lang`        | `Integer`, `Long`, `Float`, `Double`, `Byte`, `Short`, `Character`, `Boolean`, `Number`, `Record`                                                            |
| `java.util`        | `Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`                                                                                                  |
| `java.time`        | `LocalDate`, `LocalTime`, `LocalDateTime`, `ZonedDateTime`, `OffsetTime`, `OffsetDateTime`, `Duration`, `Instant`, `Period`, `Year`, `YearMonth`, `MonthDay` |
| `java.time.chrono` | `MinguoDate`, `HijrahDate`, `JapaneseDate`, `ThaiBuddhistDate`                                                                                               |

為了盡可能降低相容性風險，這些類的規範長期以來就一直不鼓勵依賴其實例身份，並且一直將它們定義為[基於值的類（value-based classes）](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/doc-files/ValueBased.html)。這些類也一直不鼓勵、甚至阻止使用者透過構造器直接建立實例。自 Java 16 起，[針對基於值的類所產生的警告](https://openjdk.org/jeps/390)已經開始阻止開發者在這些類的實例上執行同步。

絕大多數平台 API 都可以無縫支援值物件。接受 `Object` 或 `Object[]` 參數的方法也可以接受值物件。幾乎所有需要提供介面實現的地方，實現類都可以是值類。`List<T>` 和 `Comparable<T>` 等泛型類型，也可以使用值類作為類型參數進行實例化。

平台 API 還做了其他一些修改，以進一步支援值物件：

- `java.util.Objects` 類新增了兩個方法：[`hasIdentity`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/Objects.html#hasIdentity(java.lang.Object)>) 和 [`requireIdentity`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/Objects.html#requireIdentity(T,java.util.function.Supplier)>)，用於區分身份物件和值物件。

- `java.lang.reflect.AccessFlag` 中新增了常量 [`IDENTITY`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/AccessFlag.html#IDENTITY)，用於指出一個類是否為身份類。

  一個類屬於身份類還是值類，會記錄在它的 class 文件中。身份類會設定 `ACC_IDENTITY` 標誌；值類則不會。這個標誌取代了傳統的 `ACC_SUPER` 標誌。JVM 規範一直建議編譯器和工具在 class 文件中設定 `ACC_SUPER` 標誌，因此預設情況下，編譯器和工具仍會繼續在新 class 文件中設定該標誌，從而生成身份類。

- :span{#serialization}value record 的序列化可以自動工作，但非 record 值類的序列化需要手動處理。實現 `Serializable` 的值類必須實現 [`writeReplace`](https://download.java.net/java/early_access/jdk28/docs/specs/serialization/output.html#the-writereplace-method) 和 [`readResolve`](https://download.java.net/java/early_access/jdk28/docs/specs/serialization/input.html#the-readresolve-method) 方法，以便在序列化和反序列化時使用替代物件，而不是直接處理值物件本身。如果沒有實現這些方法，嘗試序列化或反序列化值物件時就會拋出 `InvalidClassException`。

  必須這樣做，是因為值類使用[嚴格初始化欄位](https://openjdk.org/jeps/539)機制進行編譯，而反序列化無法安全地初始化這類欄位。值物件只能透過呼叫構造器來建立，並由構造器初始化其欄位。未來，我們預計會增強序列化機制，使可序列化的值類能夠自動完成序列化和反序列化。

  對於那些在執行時無法完成序列化的值類，`javac` 會產生 `serial` 警告。

- :span{#reflection}不支援透過[深度反射（deep reflection）](https://openjdk.org/jeps/8305968#Undermining-integrity)修改值物件的欄位，例如使用 `java.lang.reflect.Field` API 中的 [`setAccessible`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/Field.html#setAccessible(boolean)>) 和 [`set`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/Field.html#set(java.lang.Object,java.lang.Object)>) 方法。透過深度反射修改 `final` 欄位的庫與安全構造機制不相容。即使命令列中提供了 [`--enable-final-field-mutation`](https://openjdk.org/jeps/500#Description) 選項，也不允許修改值物件的欄位。庫必須透過值類自身的構造器來初始化實例。

- [`java.lang.ref`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/ref/package-summary.html) 包中的垃圾回收相關 API，以及 [`java.util.WeakHashMap`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/WeakHashMap.html)，不能用於值物件。嘗試為值物件建立 `Reference` 物件時，會拋出 `IdentityException`。

  從 JDK 25 開始，當基於值的類與這些 API 一起使用時，`javac` 已經會產生 [`identity` 警告](https://bugs.openjdk.org/browse/JDK-8354556)。從 JDK 28 開始，當值類與這些 API 一起使用時，`javac` 同樣會產生 `identity` 警告。

### 值物件的執行時最佳化

在執行時，JVM 可以使用比身份物件引用更緊湊的編碼方式來最佳化值物件引用。JVM 不必在堆上為值物件單獨分配空間，而是可以對物件引用進行*扁平化（flatten）*和*標量化（scalarize）*。

- _引用扁平化（Reference flattening）：_ 當一個物件的欄位或陣列元素儲存了對另一個物件的引用時，JVM 可以把被引用物件的欄位值直接編碼到這個引用所在的位置中。此時，這個引用不再是一個指向記憶體中另一個物件的指標。這樣的引用稱為被*扁平化（flattened）*。

- _引用標量化（Reference scalarization）：_ 當方法參數或局部變數儲存了物件引用時，JVM 可以把物件的欄位值分別編碼到額外的局部變數中。此時，這個引用同樣不再是指向記憶體中物件的指標。這樣的引用稱為被*標量化（scalarized）*。

當一個引用被扁平化或標量化後，它就不再需要在堆上擁有獨立的物件表示。這意味著它不會給垃圾回收帶來額外負擔，而且它的資料會始終與引用它的物件或目前呼叫堆疊位於相鄰的記憶體位置。

### 引用扁平化

例如，JVM 可以對 `Integer` 引用陣列進行扁平化，使每個陣列元素中的引用直接編碼底層整數值，而不是指向某個 `Integer` 物件的記憶體位置。每個引用還要表示原來的 `Integer` 引用是否為 `null`，因此可以在整數值前加一個標誌：`0` 表示 `null`，`1` 表示非 `null`：

```text
+--------------+
| Integer[5]   |
+--------------+
| 1|1996       |
| 1|2006       |
| 1|1996       |
| 0|0          |
| 0|0          |
+--------------+
```

每個 `int` 值占 32 位，而每個 `null` 標誌至少還需要 1 位。受硬體限制，JVM 很可能會把每個扁平化後的 `Integer` 引用編碼成一個 64 位字。因此，`Integer` 陣列的記憶體占用仍然會大於普通 `int` 陣列，但遠小於由一組指向 `Integer` 物件的指標構成的陣列的總記憶體占用。（每個指標本身是一個 32 位或 64 位值，而每個被引用物件僅物件頭就至少需要[64 位](https://openjdk.org/jeps/450)。）更重要的是，所有 `Integer` 資料都會直接儲存在陣列本身內部，訪問時不需要額外的記憶體載入。

如前文所示，`LocalDate` 引用陣列也可以進行扁平化：在一個 `LocalDate` 物件的「年-月-日」三元組（一個 `int` 和兩個 `byte`）之前加上一個 `null` 標誌。與扁平化後的 `Integer` 引用一樣，這種 `LocalDate` 引用也可以裝進 64 位：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 1|1996|01|23 |
| 1|1996|01|23 |
| 1|2026|01|23 |
| 0|0000|00|00 |
| 1|1996|01|23 |
+--------------+
```

欄位同樣可以儲存扁平化引用。例如，一個 `LocalDateTime` 物件有兩個欄位，一個 `LocalDate` 和一個 `LocalTime`，它們都可以儲存扁平化引用：

```text
+----------------------+
| LocalDateTime        |
+----------------------+
| date=1|2026|01|23    |
| time=1|09|00|00|0000 |
+----------------------+
```

引用扁平化必須保證資料完整性。扁平化引用必須始終以原子方式讀寫，否則資料可能損壞。在常見硬體架構上，這意味著儲存扁平化引用的可變欄位大小通常不能超過 64 位。

例如，如果嘗試把一個 `LocalDateTime` 物件的引用扁平化，就需要嵌入底層 `LocalDate` 和 `LocalTime` 物件的欄位、兩者各自的 `null` 標誌，以及 `LocalDateTime` 自身的 `null` 標誌。最終的扁平化引用很可能太大，無法進行原子讀寫，因此 JVM 無法把它直接存入一個 `LocalDateTime` 類型的可變欄位中，例如身份類 `Button` 的 `lastClicked` 欄位：

```text
+--------------------------------------------+
| Button                                     |
+--------------------------------------------+
| lastClicked=1|1|2026|01|23|1|09|00|00|0000 |  // Not possible
| ...                                        |
+--------------------------------------------+
```

相反，JVM 會自行、靜默地選擇一種適用於可變 `lastClicked` 欄位的引用布局。例如，這個欄位可以繼續儲存指向 `LocalDateTime` 物件的指標，而這個 `LocalDateTime` 物件自身的欄位則可以像前文那樣儲存扁平化引用：

```text
+----------------------+
| Button               |
+----------------------+
| lastClicked=87fa50a0 |------> +----------------------+
| ...                  |        | LocalDateTime        |
+----------------------+        +----------------------+
                                | date=1|2026|01|23    |
                                | time=1|09|00|00|0000 |
                                +----------------------+
```

相比之下，值類的欄位沒有這種原子性限制，因為值物件的欄位永遠不會被觀察到正在發生修改。因此，例如值類 `Event` 中的 `timestamp` 欄位就可以儲存一個扁平化後的 `LocalDateTime` 引用：

```text
+------------------------------------------+
| Event                                    |
+------------------------------------------+
| timestamp=1|1|2026|01|23|1|09|00|00|0000 |  // OK in a value class
| ...                                      |
+------------------------------------------+
```

未來的增強可能讓 64 位甚至更大的值物件引用也能夠得到更廣泛的扁平化。例如，新的語言特性可能允許值類主動放棄某些原子性約束，或者某些硬體架構未來可能切實支援 128 位原子可變欄位。

### 引用標量化

當 JVM 從堆中某個物件的欄位讀取扁平化引用時，需要把這個引用解碼成便於後續操作的形式。對於經過 JVM 即時編譯器（JIT）編譯的程式碼，這種形式可以是標量化引用。

例如，考慮下面這段程式碼：

```java
LocalDate d = dates[0];
dates[0] = d.plusYears(30);
```

`LocalDate.plusYears` 方法本身可能宣告為：

```java
public LocalDate plusYears(long yearsToAdd) {
    int newYear = YEAR.checkValidIntValue(this.year + yearsToAdd);
    return new LocalDate(newYear, this.month, this.day);
}
```

使用虛擬碼表示，JIT 編譯後的 `plusYears` 方法可能類似下面這樣。這裡使用 `{ ... }` 表示 JIT 編譯的方法能夠返回多個值；這純粹是一種記法，執行時並不存在任何包裝物件：

```text
static { boolean, int, byte, byte }
    plusYears(boolean this_null,
              int this_year, byte this_month, byte this_day,
              long yearsToAdd)
{
    if (this_null) throw new NullPointerException();
    int newYear = YEAR.checkValidIntValue(this_year + yearsToAdd);
    return { false, newYear, this_month, this_day };
}
```

那麼，更新 `dates` 陣列的那段程式碼經過 JIT 編譯後，可能類似這樣：

```text
{ d_null, d_year, d_month, d_day } = dates[0];
dates[0] = plusYears(d_null, d_year, d_month, d_day, 30);
```

得益於 JVM 的最佳化，這段程式碼從始至終都不需要接觸任何指向堆上 `LocalDate` 物件的指標：

- 讀取 `dates[0]` 時，其中的扁平化引用會轉換為標量化引用；

- `plusYears` 會返回一個新的標量化引用；以及

- 寫回陣列時，這個引用又會轉換成另一個扁平化引用。

與引用扁平化不同，引用標量化不受資料大小約束。在堆疊上壓入和彈出的局部變數不存在資料競爭風險。因此，即使 `LocalDateTime` 的標量化表示比較大，也完全可以正常操作：底層 `LocalDate` 包含三個值和一個 `null` 標誌，底層 `LocalTime` 包含四個值和一個 `null` 標誌，再加上 `LocalDateTime` 自身的一個 `null` 標誌。

JVM 長期以來已經使用[類似技術](https://docs.oracle.com/en/java/javase/26/vm/java-hotspot-virtual-machine-performance-enhancements.html#GUID-6BD8FCB5-995B-4AE9-BFAA-B2C7DE2BA5CD)對身份物件的引用進行標量化，只要它能夠證明物件的身份從未被使用。對於值物件而言，引用標量化會更加可預測，適用範圍也更加廣泛，甚至能夠跨越方法邊界。

### 何時可以進行扁平化和標量化？

引用扁平化和標量化屬於最佳化手段，而不是語言特性。開發者無法直接控制它們。和其他所有最佳化一樣，是否應用這些技術完全由 JVM 自行決定。不過，開發者仍然可以採取一些措施，讓 JVM 更有可能應用這些最佳化。

首先，扁平化和標量化要求一個變數只能儲存某個具體值類的實例引用。例如，`LocalDateTime` 物件的 `date` 欄位始終儲存 `LocalDate` 引用。對於宣告為某個值類超類型的變數（例如 `Object`），通常無法進行扁平化或標量化。

例如，下面兩個陣列建立時儲存的是相同的 `Integer` 值，但由於第二個陣列未來可以儲存任意 `Object` 引用，JVM 必須把它的元素編碼成指向堆中普通物件的指標：

```java
Integer[] ints = { 1996, 2006, 1996, null, null };  // flattenable
Object[] objs = { 1996, 2006, 1996, null, null };   // not flattenable
```

寫入 `objs` 陣列的值物件必須轉換成普通的堆物件形式：

```java
Integer i = -1;
ints[3] = i;  // write a flattened reference
objs[3] = i;  // write a heap pointer
```

泛型類型 `T` 的欄位通常會擦除成 `Object`，因此在執行時，它的行為與 `Object` 類型欄位類似：

```java
record Box<T>(T field) { }     // field is not flattenable
var b = new Box<Integer>(i);  // field stores a heap pointer
```

這些不同編碼形式之間的轉換不會產生任何語義影響：`objs` 和 `field` 所引用的 `Integer` 物件依然是值物件，並不具有身份。JVM 只是用不同的方式編碼同一個值物件。

同樣的原則也適用於方法參數：`LocalDate` 類型的參數通常可以可靠地進行標量化，而 `Object` 或 `T` 類型的參數則不行。（不過，如果方法呼叫能夠被行內，JIT 仍然可能完全跳過相關賦值和堆分配。）

影響 JVM 是否能夠進行扁平化和標量化的第二個因素，是使用值類的 class 文件內容。一個類在編譯時，其欄位和方法簽名中提到的值類名稱會記錄在新的 class 文件屬性 `LoadableDescriptors` 中。這個屬性使 JVM 能夠足夠早地載入這些值類，從而建立扁平化欄位和標量化方法參數。

如果值類 `V` 沒有列在 `C.class` 的 `LoadableDescriptors` 屬性中，那麼 JVM 在載入 `C` 時可能還不知道 `V` 是值類。實際而言，這意味著：如果一個已有的類 `V` 後來被遷移成值類，那麼為了獲得最佳性能，此前針對舊版 `V` 編譯的其他類最好重新編譯。

當引用無法進行扁平化或標量化時，JVM 會使用普通引用，指向堆中分配的物件。在非最佳情況下，這可能導致每次讀取欄位或呼叫方法時都分配一個新物件。這種情況最常見於程式的預熱階段，也就是 JVM 的 JIT 尚未生成最佳化程式碼之前。

## 後續工作

- [JEP 402](https://openjdk.org/jeps/402)，_增強的基本類型裝箱（Enhanced Primitive Boxing）_，將改進基本類型的處理方式，使其能夠利用裝箱為值物件後更輕量的特性。

- [JEP 218](https://openjdk.org/jeps/218)，_支援基本類型的泛型（Generics over Primitive Types）_（經修訂），將允許泛型類和泛型方法在使用值類類型作為類型參數時，對欄位、陣列和局部變數的布局進行特化。

## 替代方案

- 如前文所述，JVM 長期以來都會執行逃逸分析，用來識別那些在整個生命週期內從未依賴身份、因而可以進行標量化的物件。不過，這類最佳化在一定程度上不可預測，而且對逃出最佳化作用域的物件無能為力，例如儲存在欄位或陣列中的物件。

- C 語言及其相關語言支援 `struct` 以及類似類抽象的扁平化儲存。例如，C# 語言提供了[值類型（value types）](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/value-types)。與本文的值物件不同，這些抽象結構的實例具有身份，這意味著它們支援欄位修改等操作。因此，賦值、方法呼叫等場景中的複製語義都必須謹慎規定，從而帶來更複雜的使用者模型，也減少了執行時實現的自由度。我們更傾向於本文的方案，把這些底層細節交由 JVM 實現者自行決定。

## 風險與假設

- 這一特性對 Java 物件模型做出了重大修改。開發者可能會對 `==` 運算符和 `synchronized` 關鍵字的行為變化感到意外，也可能因此遇到 bug。我們預計這類影響會比較少見，而且通常可以處理。

- 某些變化可能影響身份物件的效能。例如，[`if_acmpeq`](https://download.java.net/java/early_access/jdk28/docs/specs/jvms/jvms-6.html#jvms-6.5.if_acmp_cond) 位元組碼（也就是 `==`）通常只需要一個指令週期，但現在還需要額外檢查一次，以判斷物件是不是值物件。不過，身份類這一常見情況可以最佳化成快速路徑，我們相信已經把潛在的效能回退控制在最低程度。

- `==` 運算符和 `identityHashCode` 方法可能間接暴露 `private` 欄位的值，因此存在安全風險。此外，在比較由大量值物件組成的兩棵大型樹結構時，`==` 運算符的執行時間沒有固定上限。開發者需要理解這些風險。

## 依賴項

[JEP 539](https://openjdk.org/jeps/539)，_JVM 中的嚴格欄位初始化（Strict Field Initialization in the JVM）_，提供了一種機制，通過位元組碼驗證強制要求值物件的欄位必須在早期構造階段完成初始化。
