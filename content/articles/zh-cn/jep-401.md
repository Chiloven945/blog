## 概要

引入*值对象（value object）*。值对象是不可变的，并且没有对象身份（object identity）。值对象完全由其字段值来区分，因此 Java 虚拟机可以采用有助于提升性能的方式来表示它们。这是一项[预览语言和 VM 特性](https://openjdk.org/jeps/12)。

## 目标

- 让开发者可以选择一种面向不可变数据的编程模型；在这种模型中，`==` 运算符以及其他所有操作都依据对象字段的值，而不是对象身份来区分对象。

- 支持将现有的不可变数据类以兼容方式迁移到这一模型。将 Java 平台 API 中适合的现有类（例如 `Integer` 和 `LocalDate`）迁移为其实例属于值对象的类。

- 不要求开发者学习新的内存管理或变量存储语义。Java 语言仍然只处理两类数据：基本类型值和对象引用。

- 尽可能扩大 JVM 实现者的自由度，使其能够用有助于改善内存占用、局部性和垃圾回收效率的方式表示不可变数据。

## 非目标

- 本提案不以自动将现有类的实例视为值对象为目标。值对象并非在所有方面都与其他对象采用相同的工作方式，因此类的作者必须显式选择让该类的实例成为值对象。

- 本提案不以修改 `==` 运算符、使其能够替代 `equals` 方法为目标。我们只会在适应这种新的、无身份对象所必需的范围内重新定义 `==`。在大多数场景中比较对象时应使用 `equals` 方法，这一惯常建议仍然适用。

- 本提案不以引入类似 [C](<https://en.wikipedia.org/wiki/Struct_(C_programming_language)>) 和 [C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/struct) 中的 `struct` 特性为目标。

- 本提案不以改变基本类型的处理方式为目标。基本类型在许多方面的行为与值对象相似，但两者仍是不同的概念。

- 本提案不保证任何特定的优化策略或内存布局。本提案使许多优化成为可能，但初期只会实现其中一部分。某些优化（例如不为 `null` 预留表示空间的布局）要等到未来的语言和 JVM 增强之后才可能实现。

## 动机

很多简单的数据值都是不可变的，例如复数、像素颜色、时间、日期等。我们通常使用类来建模这类值：类中只包含构造、校验和转换实例所需的逻辑，并定义 `equals`、`hashCode` 和 `toString` 方法，使等价的实例可以互换使用。

例如，平台 API 中的 [`LocalDate`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/time/LocalDate.html) 类用于表示日期：

```text
jshell> LocalDate d1 = LocalDate.of(1996, 1, 23)
d1 ==> 1996-01-23

jshell> LocalDate d2 = d1.plusYears(30)
d2 ==> 2026-01-23

jshell> LocalDate d3 = d2.minusYears(30)
d3 ==> 1996-01-23

jshell> d1.equals(d3)
$4 ==> true
```

直观地说，一个 `LocalDate` 对象的本质在于它的年、月、日三个值。但在 Java 语言中，任何对象的本质都包括它的*身份（identity）*。每当 `LocalDate.of` 方法调用 `new LocalDate(...)` 时，JVM 都会创建一个具有唯一身份的新对象，使它能够与系统中的其他所有对象区分开来。

观察对象身份最简单的方式，就是使用 `==` 运算符：

```text
jshell> d1 == d3
$6 ==> false
```

尽管 `d1` 和 `d3` 表示同一个“年-月-日”三元组——也就是说，`d1.equals(d3)` 为 `true`——它们仍然是两个身份不同的对象。

### 不可变数据不需要身份

对于可变对象来说，身份非常重要：它让我们能够区分两个当前状态相同、但未来状态可能不同的对象。假设有一个文本编辑应用，其中每一行文本都由 `Line` 类的实例表示。该类唯一的字段是一个字符列表，用户编辑这一行时就会修改这个列表。两个 `Line` 对象可能包含内容相同的字符列表，因此当前看起来也是等价的，但这只是偶然；当用户修改其中一行时，应用会修改对应对象中的字符列表，而不会修改另一个对象，它依靠对象身份来确保改动落在正确的对象上。

换句话说，可变对象不能彼此互换；而大多数不可变数据值都可以互换。两个都表示 `1996-01-23` 的 `LocalDate` 对象之间没有实际差别，因为它们的状态固定不变。无论现在还是将来，它们都表示同一个值，因此没有必要通过身份来区分这两个对象。

事实上，当对象既不可变又可互换时，对象身份反而容易造成困惑。很多人都经历过不小心使用 `==` 比较对象——例如上面的 `d1 == d3`——结果明明对象的状态和行为看起来完全相同，却得到了 `false`，让人摸不着头脑。

更糟的是，对象身份还可能暴露原本只是实现细节的选择，从而产生令人意外的行为。例如，`Integer` 类会使用一个[缓存](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/Integer.html#valueOf(int)>)，以避免创建不必要的、具有唯一身份的 `Integer` 对象。比如，通常只会有一个表示数值 `1` 的 `Integer` 对象。但缓存大小是固定的，并不会覆盖像 `1996` 这样更大的 `int` 值：

```text
jshell> Integer i = 1, j = 1;
i ==> 1
j ==> 1

jshell> i == j
$3 ==> true

jshell> Integer x = 1996, y = 1996;
x ==> 1996
y ==> 1996

jshell> x == y
$6 ==> false
```

如果那些从状态和行为上看已经可以彼此互换的对象，不再受“必须拥有不同身份”这一传统要求的约束，我们就可以避免这类意外结果。

### 对象身份在运行时是有成本的

Java 语言要求每个对象都具有身份，无论这个身份是否真的需要，这会成为性能上的负担。JVM 因而必须为每个新创建的对象分配内存，使它能够与系统中已经存在的所有其他对象区分开来；而每次使用对象时，又都需要访问相应的内存。

例如，假设程序创建了 `int` 值数组和 `LocalDate` 引用数组：

```text
jshell> int[] ints = { 1996, 2006, 1996, 1, 23 }
ints ==> int[5] { 1996, 2006, 1996, 1, 23 }

jshell> LocalDate[] dates = { d1, d1, d2, null, d3 }
dates ==> LocalDate[5] { 1996-01-23, 1996-01-23, 2026-01-23,
                         null, 1996-01-23 }
```

`int` 数组可以表示成一块连续的内存，其中直接保存 `int` 值：

```text
+----------+
| int[5]   |
+----------+
| 1996     |
| 2006     |
| 1996     |
| 1        |
| 23       |
+----------+
```

相比之下，`LocalDate` 数组必须表示为一块存放一系列指针的内存；每个指针再指向另一块表示 `LocalDate` 对象的内存：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 87fa1a09     | -----------------------> +-----------+
| 87fa1a09     | -----------------------> | LocalDate |
| 87fb4ad2     | ------> +-----------+    +-----------+
| 00000000     |         | LocalDate |    | y=1996    |
| 87fb5366     | ---     +-----------+    | m=1       |
+--------------+   |     | y=2026    |    | d=23      |
                   v     | m=1       |    +-----------+
        +-----------+    | d=23      |
        | LocalDate |    +-----------+
        +-----------+
        | y=1996    |
        | m=1       |
        | d=23      |
        +-----------+
```

尽管 `LocalDate` 数组所表示的数据并不比 `int` 数组复杂多少——一个“年-月-日”三元组本质上只是 48 位基本类型数据——但因为存在指针和单独分配的对象，它的内存占用要大得多。

更糟的是，当程序遍历 `LocalDate` 数组时，可能需要逐一解引用这些指针。现代 CPU 会通过缓存称为[缓存行（cache line）](https://en.wikipedia.org/wiki/CPU_cache#CACHE-LINES)的小块内存来提升性能。如果各个 `LocalDate` 对象是在不同时间创建的，或者后来被垃圾收集器移动过，那么它们在内存中的地址可能相距很远。由此造成较差的[引用局部性](https://en.wikipedia.org/wiki/Locality_of_reference)，可能使每次解引用都不得不从内存加载不同的缓存行，从而降低性能。

走投无路时，我们可能会尝试通过尽量少创建对象来提高性能，以减轻垃圾收集器的压力并改善引用局部性。例如，与其使用 `LocalDate` 对象，我们可以用 `int` 值来表示日期，让它记录[自 1970-01-01 起经过的天数](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/time/chrono/ChronoLocalDate.html#toEpochDay()>)。遗憾的是，这样做会放弃类所提供的、让 Java 代码易于维护的许多能力：有意义的名称、私有状态、构造器中的数据校验、便捷方法等等。开发者很容易忘记——或者同事压根不知道——这些表示日期的 `int` 是以 1970-01-01 而不是其他某个日期为基准，从而引入难以诊断的错误。

### 在没有身份的情况下编程

每天都会创建数以万亿计的 Java 对象，每一个都带着唯一身份。我们应该让开发者决定：程序中的哪些对象需要身份，哪些不需要。像 `LocalDate` 这样表示简单不可变数据的类，其作者应该能够选择放弃身份。两个都表示日期 `1996-01-23` 的 `LocalDate` 对象应该不可区分，就像两个都表示数字 `4` 的 `int` 值不可区分一样。

选择放弃身份，也就等于选择了一种兼得两方面优点的编程模型：既保留类所提供的抽象能力，又获得基本类型的简洁性和性能优势。

未来，这一编程模型还将支持新的 Java 平台 API，例如表示不同整数和浮点数形式的类，以及新的 Java 语言特性，例如面向不可变数据的用户自定义转换和数学运算符。

## 描述

我们引入*值对象（value object）*来表示简单的不可变数据。值对象是*值类（value class）*的实例；值类使用 `value` 修饰符声明。没有 `value` 修饰符的类称为*身份类（identity class）*，其实例称为*身份对象（identity object）*。

Java 程序通过*引用（reference）*操作对象。对象引用存储在变量中，使我们能够找到对象的字段。传统上，在 JVM 中，引用表示为指向内存位置的指针，因此也编码了每个对象的唯一身份。每次调用 `new` 运算符，都会在一块新的内存中分配一个全新对象并返回一个唯一引用。传统上，`==` 运算符通过比较指针来比较引用，所以即使两个被引用的对象可以互换，只要它们是两个不同对象，对应的引用也不会满足 `==`。

值对象则不同。值对象的引用同样存储在变量中，并使我们能够找到对象的字段；但在 JVM 中，它不一定用指针表示，因此也不一定编码对象的唯一身份。对于值类，调用 `new` 运算符未必真的分配一个新对象；它可能返回一个已经存在的对象的引用，甚至可能返回一个直接承载对象内容的引用。`==` 运算符比较值对象引用时，会比较对象的字段值，因此如果两个对象拥有完全相同的字段值，对应的引用就满足 `==`。

对不可变数据使用值对象，可以节省内存并提升性能。由于程序无法区分两个字段值完全相同的值对象——即使使用 `==` 运算符也不行——JVM 就可以在不影响程序行为的前提下改变值对象的内存布局。例如，JVM 可以把值对象的字段保存在栈上，甚至直接保存在 CPU 寄存器里，而不是放在堆上。

### 值对象是一项默认关闭的[预览语言和 VM 特性](https://openjdk.org/jeps/12)

要在 JDK 28 中使用这一特性，必须启用预览特性：

- 使用 `javac --release 28 --enable-preview Main.java` 编译程序，并使用 `java --enable-preview Main` 运行；或者，

- 使用[源码启动器](https://openjdk.org/jeps/330)时，通过 `java --enable-preview Main.java` 运行程序；或者，

- 使用 [jshell](https://openjdk.org/jeps/222) 时，通过 `jshell --enable-preview` 启动。

Java 平台 API 中的[某些类](#java-平台中的值类)只有在启用预览特性时才会成为值类；否则，它们的行为与 JDK 27 中完全相同。

例如，如果代码引用了 `LocalDate` 类，而编译时没有启用预览特性，那么编译器会使用现有的身份对象版本 `LocalDate`，运行程序时也无需启用预览特性。但如果编译时启用了预览特性，编译器就会使用新的值对象版本 `LocalDate`，运行程序时也必须启用预览特性。启用预览特性后，无法再使用 `LocalDate` 的身份对象版本。

### 使用值对象进行编程

Java 平台 API 中现在有 30 个类被声明为值类，例如：

| 包        | 类                                                                            |
| --------- | ----------------------------------------------------------------------------- |
| java.lang | `Integer`, `Long`, `Float`, `Double`, `Byte`, `Short`, `Character`, `Boolean` |
| java.util | `Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`                   |
| java.time | `LocalDate`, `LocalTime`, `LocalDateTime`, `ZonedDateTime`, `Duration`        |

这些类的所有实例都是值对象。其中包括作为 `Integer`、`Long` 等类实例的[装箱基本类型值](https://download.java.net/java/early_access/jdk28/docs/specs/jls/jls-5.html#jls-5.1.7)。`==` 运算符按字段值比较值对象，因此，例如，如果两个 `Integer` 对象表示同一个基本类型值，它们就满足 `==`：

```text
$ jshell --enable-preview
|  Welcome to JShell -- Version 28-internal
|  For an introduction type: /help intro

jshell> Integer x = 1996, y = 1996;
x ==> 1996
y ==> 1996

jshell> x == y
$3 ==> true
```

同样，只要两个 `LocalDate` 对象拥有相同的年、月、日值，它们就满足 `==`：

```text
jshell> LocalDate d1 = LocalDate.of(1996, 1, 23)
d1 ==> 1996-01-23

jshell> LocalDate d2 = d1.plusYears(30)
d2 ==> 2026-01-23

jshell> LocalDate d3 = d2.minusYears(30)
d3 ==> 1996-01-23

jshell> d1 == d3
$7 ==> true
```

可以使用新的 `Objects.hasIdentity` 方法来观察某个对象是否为身份对象：

```text
jshell> Objects.hasIdentity(d1)
$8 ==> false
```

由于 `String` 类的 API 和实现中存在一些对对象身份的依赖，因此它不是值类，所以 `String` 的实例始终是身份对象：

```text
jshell> String s = "abcd"
s ==> "abcd"

jshell> Objects.hasIdentity(s)
$10 ==> true

jshell> String t = "aabcd".substring(1)
t ==> "abcd"

jshell> s == t
$12 ==> false
```

在大多数方面，值对象与 Java 语言中一贯的对象工作方式相同：它们有字段和方法，通过引用来操作，而且引用可以为 `null`。

不过，值对象不支持少数依赖身份的操作，其中包括同步：

```text
jshell> synchronized (d1) { d1.notify(); }
|  Error:
|  unexpected type
|    required: a type with identity
|    found:    java.time.LocalDate
|  synchronized (d1) { d1.notify(); }
|  ^--------------------------------^

jshell> Object o = d1
o ==> 1996-01-23

jshell> synchronized (o) { o.notify(); }
|  Exception java.lang.IdentityException: Cannot synchronize on
   an instance of value class java.time.LocalDate
|        at (#19:1)
```

JVM 实现者可以自由决定值对象引用在运行时的编码方式，以优化内存占用、局部性和垃圾回收效率。例如，前文曾看到下面这个通过指针指向堆对象实现的数组：

```text
jshell> LocalDate[] dates = { d1, d1, d2, null, d3 }
dates ==> LocalDate[5] { 1996-01-23, 1996-01-23, 2026-01-23,
                         null, 1996-01-23 }
```

现在，由于 `LocalDate` 对象没有身份，JVM 不必再使用指针表示它们的引用，而可以把 `LocalDate` 对象的字段直接编码进引用。`dates` 数组中的每个元素都可以表示为一个 64 位字：它先表示引用是否为 `null`；如果不是 `null`，就直接保存值对象的年、月、日字段值：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 1|1996|01|23 |
| 1|1996|01|23 |
| 1|2026|01|23 |
| 0|0000|00|00 |
| 1|1996|01|23 |
+--------------+
```

这种 `LocalDate` 数组的性能特征可能与普通 `int` 数组类似，同时拥有更低的内存占用和更好的引用局部性：

```text
+----------+
| int[5]   |
+----------+
| 1996     |
| 2006     |
| 1996     |
| 1        |
| 23       |
+----------+
```

这只是一种可能的优化方式；有些值类（例如 `LocalDateTime`）太大，无法利用这种具体技术。不过，没有身份这一点仍然让 JVM 实现者能够以多种方式优化值对象引用。

### 声明值类

可以在任何其实例应当保持不可变并且可互换的类上使用 `value` 修饰符，从而声明自己的值类：

- _不可变（Immutable）_——类的所有实例字段都是 `final`，而且一个实例所表示的值不会随时间发生变化；以及

- _可互换（Interchangeable）_——没有必要区分两个分别创建、但表示相同值的实例。

当类使用 `value` 修饰符时，其字段会隐式成为 `final`。类本身也会隐式成为 `final`，因此不能被继承。由于类是 `final`，它的方法也不能被覆盖。

值类中的字段类型没有限制。字段既可以保存对其他值对象的引用，也可以保存对身份对象（例如字符串）的引用。

[Record 类](https://openjdk.org/jeps/395)本身是 `final` 的，而且它们的所有字段也是 `final`，因此通常很适合成为值类：

```text
jshell> value record Point(int x, int y) {}
|  created record Point

jshell> Point p = new Point(17, 3)
p ==> Point[x=17, y=3]

jshell> Objects.hasIdentity(p)
$3 ==> false

jshell> new Point(17, 3) == p
$4 ==> true
```

很多类的实例同样既不可变又可以互换，但它们不能声明为 record，因为其字段并不与构造器参数完全对应；也就是说，它们并不*透明（transparent）*。这类对象可能在内部使用私有字段，以一种比公开方法所暴露的表示方式更高效的方式保存数据。例如，一个类可以为了节省内存，用一个 `long` 字段统一表示欧元和欧分；它不能成为 value record，但仍然可以成为值类：

```java
value class EURCurrency {

    private long cs;  // implicitly final

    private EURCurrency(long cs) { this.cs = cs; }

    public EURCurrency(long e, int c, boolean neg) {
        this(neg ? -e * 100 - c : e * 100 + c);
    }

    public EURCurrency(long e, int c) { this(e, c, false); }

    public long euros() { return Math.abs(cs) / 100; }
    public int cents() { return (int) Math.abs(cs) % 100; }
    public boolean negative() { return cs < 0; }

    public String toString() {
        var prefix = negative() ? "-€" : "€";
        return "%s%d,%d".formatted(prefix, euros(), cents());
    }

}
```

### 比较值对象

传统上，`==` 运算符的用途是判断两个被引用的对象是否具有相同的身份。

引入值对象后，`==` 运算符的用途变成判断两个被引用的对象是否不可区分。由于身份对象按定义就是通过身份来区分的，因此对于身份对象，Java 28 中的 `==` 与从 Java 1.0 开始一直以来的行为完全相同：它判断两个引用是否指向同一个对象——也就是同一个内存位置——或者判断两个引用是否都是 `null`。

比较两个值对象时，`==` 运算符会检查它们是否引用同一个类、并且字段值相同的实例。也就是说，两个值对象在以下条件都成立时不可区分：

- 它们是同一个值类的实例；

- 它们的基本类型字段保存相同的位模式；以及

- 它们的引用类型字段彼此不可区分，也就是递归地对这些字段应用 `==` 运算符。

满足这些条件时，JVM 就可以自由地用一个引用替换另一个，而任何代码都无法察觉差别。

对于值对象，`==` 运算符和 `equals` 方法通常会得到相同的结果。不过，对于某些值类，即使实例的字段值不同（也就是不满足 `==`），它们仍然可能是可互换的（也就是 `equals` 为 `true`）。**要判断两个值对象是否表示同一个值，应使用 `equals` 方法。声明类时，应当以这样一种方式定义 `equals`：对于可互换的实例，它始终返回 `true`。**

下面的 `Substring` 值类说明了某些值对象中 `==` 和 `equals` 可能产生不同结果的情况。这个类表示字符串的一个子串，但不会在内存中重新分配一个新的 `char[]`。一个 `Substring` 实例的内部状态由源字符串和两个位置坐标组成，而该实例所表示的值则是 `toString` 产生的字符序列。因此，两个实例可能表示相同的字符序列（也就是 `equals` 为 `true`），但内部状态不同（也就是不满足 `==`）。

```java
value class Substring {

    private String str;
    private int start, end;

    public Substring(String s, int i, int j) {
        str = s; start = i; end = j;
    }

    public String toString() {
        return str.substring(start, end);
    }

    public boolean equals(Object o) {
        return o instanceof Substring && toString().equals(o.toString());
    }

    public int hashCode() {
        return Objects.hash(Substring.class, toString());
    }

}

jshell> Substring sub1 = new Substring("ringing", 1, 4);
sub1 ==> ing

jshell> Substring sub2 = new Substring("ringing", 4, 7);
sub2 ==> ing

jshell> sub1.equals(sub2)
$3 ==> true

jshell> sub1 == sub2
$4 ==> false
```

如果两个值对象的字段分别引用两个不同的身份对象，而这两个身份对象根据 `equals` 判断又是可互换的，那么 `==` 与 `equals` 的结果同样可能不同：

```text
jshell> String r = "bringing".substring(1);
r ==> ringing

jshell> r == "ringing"
$6 ==> false

jshell> Substring sub3 = new Substring(r, 1, 4);
sub3 ==> ing

jshell> sub1.equals(sub3)
$8 ==> true

jshell> sub1 == sub3  // tests sub1.str == sub3.str
$9 ==> false
```

值对象包含 `float` 或 `double` 字段时，也是 `==` 与 `equals` 可能不同的另一种情况。基本浮点类型支持多个不同的 `NaN` 值。大多数浮点运算会把这些 `NaN` 视为可互换，但由于每个值仍然不同，封装不同 `NaN` 值的值对象可以被 `==` 运算符区分出来。声明值类时，必须自行决定这种区别对于 `equals` 方法是否有意义。例如，在 value record 中，`equals` 的默认行为会把所有 `NaN` 值都视为可互换：

```text
jshell> value record Length(float val) {}
|  created record Length

jshell> Length l1 = new Length(Float.intBitsToFloat(0x7ff80000))
l1 ==> Length[val=NaN]

jshell> Length l2 = new Length(Float.intBitsToFloat(0x7ff80001))
l2 ==> Length[val=NaN]

jshell> l1.equals(l2)
$4 ==> true

jshell> l1 == l2
$5 ==> false

jshell> Integer.toHexString(Float.floatToRawIntBits(l1.val()))
$6 ==> "0x7ff80000"

jshell> Integer.toHexString(Float.floatToRawIntBits(l2.val()))
$7 ==> "0x7ff80001"
```

（关于浮点值之间不同形式的等价关系，详见 [`Double` 类的规范](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/Double.html#fpNumericalEq)。）

由于 `==` 运算符会递归比较值对象中的引用类型字段，因此比较两个值对象时，所需的比较次数可能没有固定上限。下面的示例中，为了判断两个深层嵌套的 `Box` 对象是否不可区分，必须完整遍历整个嵌套结构：

```text
jshell> value record Box(Object val) {}
|  created record Box

jshell> var b1 = new Box(new Box(new Box(new Box(l1))))
b1 ==> Box[val=Box[val=Box[val=Box[val=Length[val=NaN]]]]]

jshell> var b2 = new Box(new Box(new Box(new Box(l2))))
b2 ==> Box[val=Box[val=Box[val=Box[val=Length[val=NaN]]]]]

jshell> b1.equals(b2)
$11 ==> true

jshell> b1 == b2
$12 ==> false
```

如[下文](#值对象的安全构造)所述，值类构造器会受到一定约束，因此递归地对值对象应用 `==` 运算符绝不会造成无限循环。不过，深度比较仍然可能耗费很长时间，甚至触发 `StackOverflowError`。

### 值类与子类化

与每个身份类一样，每个值类也都属于一个以 `java.lang.Object` 为根的类层次结构。不存在一个作为所有值类共同父类的 `java.lang.Value`。

值类可以实现接口。因此，声明为接口类型或 `Object` 类型的变量，可以同时保存值对象和身份对象的引用：

```text
jshell> Comparable<?> comp = LocalDate.of(1996, 1, 23)
comp ==> 1996-01-23

jshell> Objects.hasIdentity(comp)
$2 ==> false

jshell> comp = "abc"
comp ==> "abc"

jshell> Objects.hasIdentity(comp)
$4 ==> true
```

默认情况下，值类隐式为 `final`，不能被继承。不过，值类也可以声明为 `abstract`，从而允许其他类继承它，并允许其方法被覆盖。抽象值类的字段与具体值类一样，也隐式为 `final`。抽象值类的方法则可以像抽象身份类一样标记为 `abstract`。

将一个类声明为抽象值类，表示该类本身不需要身份。它的子类既可以是值类，也可以是身份类。（抽象值类上的 `value` 修饰符也可以理解为表示*值兼容（value-compatible）*。）

值类可以继承 `java.lang.Object` 或抽象值类，但不能继承身份类。（`Object` 在这一点上很特殊：它既不是抽象类，也不是值类，而且 `new Object()` 创建的实例具有身份，但它仍然允许值类继承。）

许多现有的抽象类，如果本来就是为公开扩展而设计的，那么很适合成为抽象值类。例如，抽象类 `Number` 没有字段，也没有任何依赖身份敏感特性的代码，因此可以安全地迁移为抽象值类：

```java
abstract value class Number implements Serializable {
    public abstract int intValue();
    public abstract long longValue();
    public byte byteValue() { return (byte) intValue(); }
    ...
}
```

值类 `Integer` 和身份类 `java.math.BigInteger` 都继承 `Number`：

```text
jshell> Number num = 123
num ==> 123

jshell> Objects.hasIdentity(num)
$2 ==> false

jshell> num = BigInteger.valueOf(123)
num ==> 123

jshell> Objects.hasIdentity(num)
$4 ==> true
```

抽象值类也可以使用 [`sealed`](https://openjdk.org/jeps/409) 来限制哪些类可以继承它：

```java
sealed abstract value class UserID
    permits EmailID, PhoneID, UsernameID
{
    ...
}

value class EmailID extends UserID {
    private String name, domain; ...
}

value class PhoneID extends UserID {
    private String digits; ...
}

value class UsernameID extends UserID {
    private String name; ...
}
```

### 值对象的安全构造

构造器通过设置字段值来初始化新创建的对象。由于值对象没有身份，其他代码只能在它们的字段值全部初始化完成之后观察到它们。

为了保证这一点，值对象的字段必须在对象被共享给其他代码之前完成赋值。这也会阻止两个值对象直接或间接地互相引用，从而确保调用 `==` 运算符时绝不会出现无限循环。

一个仍处于构造过程中的对象称为*幼体（larval）*对象：它已经被创建，但还没有完全成形。处理幼体对象时始终需要格外谨慎。如果幼体对象在构造器中被泄露给构造器之外的代码，那么对象的不变量可能尚未成立，而且外部代码甚至可能观察到 `final` 字段被修改的过程。

传统上，构造器通过调用超类构造器 `super(...)` 开始初始化。如果构造器没有显式这样做，Java 编译器就会在构造器主体开头插入一次 `super()` 调用。超类构造器返回之后，子类构造器才会继续设置自己声明的实例字段，并执行其他初始化工作。这种模式意味着，在任意超类构造器执行期间，一个子类字段完全尚未初始化的对象都有可能被泄露出去。

Java 25 引入的[灵活构造器主体（Flexible Constructor Bodies）](https://openjdk.org/jeps/513)提供了更安全的初始化机制，允许在调用 `super(...)` 之前先设置字段或执行其他代码。借助这一特性，对象初始化分成两个阶段：调用 `super(...)` 之前的*早期构造（early construction）*，以及调用之后的*后期构造（late construction）*。

在早期构造阶段，幼体对象不可能被泄露。构造器可以设置幼体对象的字段，但不能调用实例方法，也不能以其他方式使用 `this`。因此，在早期构造阶段完成初始化的字段一定会先被设置，之后才可能被读取，即使某个超类后来泄露了幼体对象也是如此。特别是，外界永远无法观察到 `final` 字段被修改。

在值类中，构造器代码始终运行在早期构造阶段。Java 编译器会把 `super()` 调用插到构造器主体末尾，而不是开头。尝试调用实例方法或以其他方式使用 `this` 都会失败：

```java
value class Name {

    String name;
    int length;

    private int strLength() {
        return name.length();
    }

    Name(String n) {
        name = n;
        length = strLength();  // Error, invokes this.strLength()
    }

}
```

带初始化表达式的实例字段会在构造器开始执行时、也就是早期构造阶段完成设置。实例初始化块是一项很少使用的特性，它们会在后期构造阶段运行；值类的实例初始化块不允许设置实例字段。

如果值类构造器中的某些代码确实需要使用 `this`，可以显式调用 `super(...)` 或 `this(...)`，以此标记从早期构造阶段切换到后期构造阶段。不过，在调用 `super(...)` 之前，必须在不引用 `this` 的情况下为该类的所有字段完成赋值：

```java
value class Name {

    String name;
    int length;

    private static int strLength(String n) {
        return n.length();
    }

    Name(String n) {
        name = n;
        length = strLength(name);  // OK, strLength is now static
        super();                   // All fields must be set at this point
        System.out.println("Name: " + this);
    }

}
```

### 其他构造增强

我们放宽了对所有幼体对象字段访问的一些限制，无论这些对象是值对象还是身份对象。在 Java 27 中，新对象的字段可以在早期构造阶段写入，但不能读取。在 Java 28 中，启用预览特性后，这些字段在早期构造阶段既可以写入，也可以读取。不过，在进入后期构造阶段之前，引用继承而来的字段、调用实例方法，或者把 `this` 共享给其他代码仍然是非法的。

此外，为了简化模型并提升性能，在 Java 28 中启用预览特性后，所有 record 类——无论是 value record 还是 identity record——都会采用与值类相同的安全构造规则。record 类的构造器始终运行在早期构造阶段。record 的字段必须在能够被观察之前完成设置，因此类的使用者始终可以预期对 component 的访问会得到一致的结果。

对于 identity record 的构造器声明而言，这一修改不具备源码兼容性，不过我们预计实际出现不兼容的情况会很少。例如，下面这个 record 类无法编译，因为它的规范构造器在早期构造阶段引用了 `this`：

```java
record Node(String label, List<Node> edges) {

    static void nullCheck(Object arg, Object owner) {
        if (arg == null) {
            String msg = "null arg for " + owner.toString();
            throw new IllegalArgumentException(msg);
        }
    }

   public Node {
        nullCheck(label, this);  // Error with --enable-preview
        nullCheck(edges, this);  // Error with --enable-preview
    }

}
```

这类不兼容情况之所以会很少，是因为如上例所示，在 record 构造器中尝试使用 `this` 往往本身就是一个 bug：当这里的代码调用 `toString()` 时，`Node` 的字段甚至还没有完成设置。对大型源码语料库中现有 record 类声明的调查也证实，record 类违反这些新规则的情况很少见。

如果 record 构造器确实必须访问 `this`，可以插入显式的 `super()` 调用，但在此之前必须先在早期构造阶段显式设置 record 的字段。

### 继承自 `java.lang.Object` 的方法

与任何类一样，值类也会继承 `java.lang.Object` 中的 `equals`、`hashCode` 和 `toString` 等方法，除非类自身覆盖了它们。这些方法传统上依赖对象身份；但当它们作用于值对象时，会改用对象字段的值。具体来说：

- 继承自 `Object.equals` 的实现会使用 `==` 运算符判断对象是否不可区分。[对于值类来说，这可能正是合适的 `equals` 行为](#比较值对象)；如果不是，类就应该覆盖 `equals` 方法。

- 继承自 `Object.hashCode` 的实现会根据对象字段的值计算哈希值。（也可以通过 `System.identityHashCode` 计算出这个值——这是一个颇为遗憾的历史遗留名称。）与通常规则一样，如果值类覆盖了 `equals`，也应同时覆盖 `hashCode`。

- 继承自 `Object.toString` 的实现会返回形如 `"ClassName@hashCode"` 的字符串。由于值类表示不可变数据，因此应该覆盖 `toString`，以更清晰地表达实例所表示的值。

在 value record 中，与所有 record 一样，`equals`、`hashCode` 和 `toString` 的默认行为会递归地将相同的操作应用到 record 的各个 component 上。

`Object` 中还有少数其他方法会与值对象发生交互：

- 对于实现了 `Cloneable` 的值类，`Object.clone` 方法会产生一个与原对象不可区分的值对象。对于值对象来说，通常所说的 `x.clone() != x` 并没有意义。声明一个保存身份对象引用的值类时，可以考虑覆盖 `clone` 方法，为这些对象创建深拷贝。

- `wait` 和 `notify` 方法要求对象已经被当前线程锁定。由于无法在值对象上进行同步，因此尝试调用这些方法时总会以 `IllegalMonitorStateException` 失败。

- 值对象的 `finalize` 方法永远不会被垃圾收集器调用。对于覆盖了 `finalize` 的值类，`javac` 会产生 `identity` 警告。

### 迁移到值类

对于任何用于表示简单不可变数据的类而言，值类和 record 都是非常有用的工具。

一般来说，如果一个状态不可变的类并不需要身份，那么它很可能适合使用 `value` 修饰符。这也包括抽象类：抽象类通常根本没有状态，因此不应该无谓地把“必须具有身份”的要求强加给它的子类。（当然，也有一些抽象类虽然没有声明可变状态，但定义了本质上属于可变模型的 API，因此不应该成为值类；还有一些具体类根本不是用来表示数据的，例如它们可能被设计成只实例化一次。）

如果一个类本身是 `final` 或 `abstract`，而且只包含 `final` 字段，那么添加或移除 `value` 关键字属于二进制兼容的修改。

不过，将身份类迁移成值类仍然存在一些值得考虑的源码和行为兼容性风险：

- 如果类具有公开构造器，现有客户端可能依赖这些构造器创建能够通过 `==` 与其他所有对象区分开的对象。把这个类改成值类后，这种逻辑就不再成立，并可能导致运行时 bug。

  如果这种不兼容风险比较严重，可以考虑弃用公开构造器，并鼓励使用工厂方法。例如，Java 9 中就弃用了 `Integer`、`Long` 等类的构造器，并建议改用相应的 `Integer.valueOf`、`Long.valueOf` 等工厂方法。

- 如果现有客户端会在该类实例上进行同步，那么迁移之后，这些代码会失败：要么在编译期报错，要么在运行时抛出 `IdentityException`。对于具有公开构造器的类，这种风险更值得关注，因为客户端可能依赖构造器创建唯一实例，并把它们用作锁。

- 如果 `equals` 和 `hashCode` 方法原先没有被覆盖，那么迁移之后它们的行为会发生变化。一个合适的迁移候选类，应当在迁移前就已经覆盖这些方法，使其行为不依赖对象身份。

- 如果类封装了敏感数据，需要注意通过 `==` 运算符或 `System.identityHashCode` 暴露这些数据的风险。恶意用户可能尝试利用这些操作推断实例内部的数据。值对象并不是为抵御这类针对敏感数据的攻击而设计的。

- 如果类实现了 `Serializable`，则可能需要特殊处理，具体参见[下文](#serialization)。此外，将其迁移为值类还可能破坏反射和垃圾回收 API 的某些用法，具体参见[下文](#reflection)，也可能影响其他依赖对象身份的专用代码。

### Java 平台中的值类

Java 平台 API 中现在有 30 个类被声明为值类：

| 包                 | 类                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `java.lang`        | `Integer`, `Long`, `Float`, `Double`, `Byte`, `Short`, `Character`, `Boolean`, `Number`, `Record`                                                            |
| `java.util`        | `Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`                                                                                                  |
| `java.time`        | `LocalDate`, `LocalTime`, `LocalDateTime`, `ZonedDateTime`, `OffsetTime`, `OffsetDateTime`, `Duration`, `Instant`, `Period`, `Year`, `YearMonth`, `MonthDay` |
| `java.time.chrono` | `MinguoDate`, `HijrahDate`, `JapaneseDate`, `ThaiBuddhistDate`                                                                                               |

为了尽可能降低兼容性风险，这些类的规范长期以来就一直不鼓励依赖其实例身份，并且一直将它们定义为[基于值的类（value-based classes）](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/doc-files/ValueBased.html)。这些类也一直不鼓励、甚至阻止用户通过构造器直接创建实例。自 Java 16 起，[针对基于值的类所产生的警告](https://openjdk.org/jeps/390)已经开始阻止开发者在这些类的实例上执行同步。

绝大多数平台 API 都可以无缝支持值对象。接受 `Object` 或 `Object[]` 参数的方法也可以接受值对象。几乎所有需要提供接口实现的地方，实现类都可以是值类。`List<T>` 和 `Comparable<T>` 等泛型类型，也可以使用值类作为类型参数进行实例化。

平台 API 还做了其他一些修改，以进一步支持值对象：

- `java.util.Objects` 类新增了两个方法：[`hasIdentity`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/Objects.html#hasIdentity(java.lang.Object)>) 和 [`requireIdentity`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/Objects.html#requireIdentity(T,java.util.function.Supplier)>)，用于区分身份对象和值对象。

- `java.lang.reflect.AccessFlag` 中新增了常量 [`IDENTITY`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/AccessFlag.html#IDENTITY)，用于指出一个类是否为身份类。

  一个类属于身份类还是值类，会记录在它的 class 文件中。身份类会设置 `ACC_IDENTITY` 标志；值类则不会。这个标志取代了传统的 `ACC_SUPER` 标志。JVM 规范一直建议编译器和工具在 class 文件中设置 `ACC_SUPER` 标志，因此默认情况下，编译器和工具仍会继续在新 class 文件中设置该标志，从而生成身份类。

- :span{#serialization}value record 的序列化可以自动工作，但非 record 值类的序列化需要手动处理。实现 `Serializable` 的值类必须实现 [`writeReplace`](https://download.java.net/java/early_access/jdk28/docs/specs/serialization/output.html#the-writereplace-method) 和 [`readResolve`](https://download.java.net/java/early_access/jdk28/docs/specs/serialization/input.html#the-readresolve-method) 方法，以便在序列化和反序列化时使用替代对象，而不是直接处理值对象本身。如果没有实现这些方法，尝试序列化或反序列化值对象时就会抛出 `InvalidClassException`。

  必须这样做，是因为值类使用[严格初始化字段](https://openjdk.org/jeps/539)机制进行编译，而反序列化无法安全地初始化这类字段。值对象只能通过调用构造器来创建，并由构造器初始化其字段。未来，我们预计会增强序列化机制，使可序列化的值类能够自动完成序列化和反序列化。

  对于那些在运行时无法完成序列化的值类，`javac` 会产生 `serial` 警告。

- :span{#reflection}不支持通过[深度反射（deep reflection）](https://openjdk.org/jeps/8305968#Undermining-integrity)修改值对象的字段，例如使用 `java.lang.reflect.Field` API 中的 [`setAccessible`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/Field.html#setAccessible(boolean)>) 和 [`set`](<https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/reflect/Field.html#set(java.lang.Object,java.lang.Object)>) 方法。通过深度反射修改 `final` 字段的库与安全构造机制不兼容。即使命令行中提供了 [`--enable-final-field-mutation`](https://openjdk.org/jeps/500#Description) 选项，也不允许修改值对象的字段。库必须通过值类自身的构造器来初始化实例。

- [`java.lang.ref`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/lang/ref/package-summary.html) 包中的垃圾回收相关 API，以及 [`java.util.WeakHashMap`](https://download.java.net/java/early_access/jdk28/docs/api/java.base/java/util/WeakHashMap.html)，不能用于值对象。尝试为值对象创建 `Reference` 对象时，会抛出 `IdentityException`。

  从 JDK 25 开始，当基于值的类与这些 API 一起使用时，`javac` 已经会产生 [`identity` 警告](https://bugs.openjdk.org/browse/JDK-8354556)。从 JDK 28 开始，当值类与这些 API 一起使用时，`javac` 同样会产生 `identity` 警告。

### 值对象的运行时优化

在运行时，JVM 可以使用比身份对象引用更紧凑的编码方式来优化值对象引用。JVM 不必在堆上为值对象单独分配空间，而是可以对对象引用进行*扁平化（flatten）*和*标量化（scalarize）*。

- _引用扁平化（Reference flattening）：_ 当一个对象的字段或数组元素保存了对另一个对象的引用时，JVM 可以把被引用对象的字段值直接编码到这个引用所在的位置中。此时，这个引用不再是一个指向内存中另一个对象的指针。这样的引用称为被*扁平化（flattened）*。

- _引用标量化（Reference scalarization）：_ 当方法参数或局部变量保存了对象引用时，JVM 可以把对象的字段值分别编码到额外的局部变量中。此时，这个引用同样不再是指向内存中对象的指针。这样的引用称为被*标量化（scalarized）*。

当一个引用被扁平化或标量化后，它就不再需要在堆上拥有独立的对象表示。这意味着它不会给垃圾回收带来额外负担，而且它的数据会始终与引用它的对象或当前调用栈位于相邻的内存位置。

### 引用扁平化

例如，JVM 可以对 `Integer` 引用数组进行扁平化，使每个数组元素中的引用直接编码底层整数值，而不是指向某个 `Integer` 对象的内存位置。每个引用还要表示原来的 `Integer` 引用是否为 `null`，因此可以在整数值前加一个标志：`0` 表示 `null`，`1` 表示非 `null`：

```text
+--------------+
| Integer[5]   |
+--------------+
| 1|1996       |
| 1|2006       |
| 1|1996       |
| 0|0          |
| 0|0          |
+--------------+
```

每个 `int` 值占 32 位，而每个 `null` 标志至少还需要 1 位。受硬件限制，JVM 很可能会把每个扁平化后的 `Integer` 引用编码成一个 64 位字。因此，`Integer` 数组的内存占用仍然会大于普通 `int` 数组，但远小于由一组指向 `Integer` 对象的指针构成的数组的总内存占用。（每个指针本身是一个 32 位或 64 位值，而每个被引用对象仅对象头就至少需要[64 位](https://openjdk.org/jeps/450)。）更重要的是，所有 `Integer` 数据都会直接保存在数组本身内部，访问时不需要额外的内存加载。

如前文所示，`LocalDate` 引用数组也可以进行扁平化：在一个 `LocalDate` 对象的“年-月-日”三元组（一个 `int` 和两个 `byte`）之前加上一个 `null` 标志。与扁平化后的 `Integer` 引用一样，这种 `LocalDate` 引用也可以装进 64 位：

```text
+--------------+
| LocalDate[5] |
+--------------+
| 1|1996|01|23 |
| 1|1996|01|23 |
| 1|2026|01|23 |
| 0|0000|00|00 |
| 1|1996|01|23 |
+--------------+
```

字段同样可以保存扁平化引用。例如，一个 `LocalDateTime` 对象有两个字段，一个 `LocalDate` 和一个 `LocalTime`，它们都可以保存扁平化引用：

```text
+----------------------+
| LocalDateTime        |
+----------------------+
| date=1|2026|01|23    |
| time=1|09|00|00|0000 |
+----------------------+
```

引用扁平化必须保证数据完整性。扁平化引用必须始终以原子方式读写，否则数据可能损坏。在常见硬件架构上，这意味着保存扁平化引用的可变字段大小通常不能超过 64 位。

例如，如果尝试把一个 `LocalDateTime` 对象的引用扁平化，就需要嵌入底层 `LocalDate` 和 `LocalTime` 对象的字段、两者各自的 `null` 标志，以及 `LocalDateTime` 自身的 `null` 标志。最终的扁平化引用很可能太大，无法进行原子读写，因此 JVM 无法把它直接存入一个 `LocalDateTime` 类型的可变字段中，例如身份类 `Button` 的 `lastClicked` 字段：

```text
+--------------------------------------------+
| Button                                     |
+--------------------------------------------+
| lastClicked=1|1|2026|01|23|1|09|00|00|0000 |  // Not possible
| ...                                        |
+--------------------------------------------+
```

相反，JVM 会自行、静默地选择一种适用于可变 `lastClicked` 字段的引用布局。例如，这个字段可以继续保存指向 `LocalDateTime` 对象的指针，而这个 `LocalDateTime` 对象自身的字段则可以像前文那样保存扁平化引用：

```text
+----------------------+
| Button               |
+----------------------+
| lastClicked=87fa50a0 |------> +----------------------+
| ...                  |        | LocalDateTime        |
+----------------------+        +----------------------+
                                | date=1|2026|01|23    |
                                | time=1|09|00|00|0000 |
                                +----------------------+
```

相比之下，值类的字段没有这种原子性限制，因为值对象的字段永远不会被观察到正在发生修改。因此，例如值类 `Event` 中的 `timestamp` 字段就可以保存一个扁平化后的 `LocalDateTime` 引用：

```text
+------------------------------------------+
| Event                                    |
+------------------------------------------+
| timestamp=1|1|2026|01|23|1|09|00|00|0000 |  // OK in a value class
| ...                                      |
+------------------------------------------+
```

未来的增强可能让 64 位甚至更大的值对象引用也能够得到更广泛的扁平化。例如，新的语言特性可能允许值类主动放弃某些原子性约束，或者某些硬件架构未来可能切实支持 128 位原子可变字段。

### 引用标量化

当 JVM 从堆中某个对象的字段读取扁平化引用时，需要把这个引用解码成便于后续操作的形式。对于经过 JVM 即时编译器（JIT）编译的代码，这种形式可以是标量化引用。

例如，考虑下面这段代码：

```java
LocalDate d = dates[0];
dates[0] = d.plusYears(30);
```

`LocalDate.plusYears` 方法本身可能声明为：

```java
public LocalDate plusYears(long yearsToAdd) {
    int newYear = YEAR.checkValidIntValue(this.year + yearsToAdd);
    return new LocalDate(newYear, this.month, this.day);
}
```

使用伪代码表示，JIT 编译后的 `plusYears` 方法可能类似下面这样。这里使用 `{ ... }` 表示 JIT 编译的方法能够返回多个值；这纯粹是一种记法，运行时并不存在任何包装对象：

```text
static { boolean, int, byte, byte }
    plusYears(boolean this_null,
              int this_year, byte this_month, byte this_day,
              long yearsToAdd)
{
    if (this_null) throw new NullPointerException();
    int newYear = YEAR.checkValidIntValue(this_year + yearsToAdd);
    return { false, newYear, this_month, this_day };
}
```

那么，更新 `dates` 数组的那段代码经过 JIT 编译后，可能类似这样：

```text
{ d_null, d_year, d_month, d_day } = dates[0];
dates[0] = plusYears(d_null, d_year, d_month, d_day, 30);
```

得益于 JVM 的优化，这段代码从始至终都不需要接触任何指向堆上 `LocalDate` 对象的指针：

- 读取 `dates[0]` 时，其中的扁平化引用会转换为标量化引用；

- `plusYears` 会返回一个新的标量化引用；以及

- 写回数组时，这个引用又会转换成另一个扁平化引用。

与引用扁平化不同，引用标量化不受数据大小约束。在栈上压入和弹出的局部变量不存在数据竞争风险。因此，即使 `LocalDateTime` 的标量化表示比较大，也完全可以正常操作：底层 `LocalDate` 包含三个值和一个 `null` 标志，底层 `LocalTime` 包含四个值和一个 `null` 标志，再加上 `LocalDateTime` 自身的一个 `null` 标志。

JVM 长期以来已经使用[类似技术](https://docs.oracle.com/en/java/javase/26/vm/java-hotspot-virtual-machine-performance-enhancements.html#GUID-6BD8FCB5-995B-4AE9-BFAA-B2C7DE2BA5CD)对身份对象的引用进行标量化，只要它能够证明对象的身份从未被使用。对于值对象而言，引用标量化会更加可预测，适用范围也更加广泛，甚至能够跨越方法边界。

### 何时可以进行扁平化和标量化？

引用扁平化和标量化属于优化手段，而不是语言特性。开发者无法直接控制它们。和其他所有优化一样，是否应用这些技术完全由 JVM 自行决定。不过，开发者仍然可以采取一些措施，让 JVM 更有可能应用这些优化。

首先，扁平化和标量化要求一个变量只能保存某个具体值类的实例引用。例如，`LocalDateTime` 对象的 `date` 字段始终保存 `LocalDate` 引用。对于声明为某个值类超类型的变量（例如 `Object`），通常无法进行扁平化或标量化。

例如，下面两个数组创建时保存的是相同的 `Integer` 值，但由于第二个数组未来可以保存任意 `Object` 引用，JVM 必须把它的元素编码成指向堆中普通对象的指针：

```java
Integer[] ints = { 1996, 2006, 1996, null, null };  // flattenable
Object[] objs = { 1996, 2006, 1996, null, null };   // not flattenable
```

写入 `objs` 数组的值对象必须转换成普通的堆对象形式：

```java
Integer i = -1;
ints[3] = i;  // write a flattened reference
objs[3] = i;  // write a heap pointer
```

泛型类型 `T` 的字段通常会擦除成 `Object`，因此在运行时，它的行为与 `Object` 类型字段类似：

```java
record Box<T>(T field) { }     // field is not flattenable
var b = new Box<Integer>(i);  // field stores a heap pointer
```

这些不同编码形式之间的转换不会产生任何语义影响：`objs` 和 `field` 所引用的 `Integer` 对象依然是值对象，并不具有身份。JVM 只是用不同的方式编码同一个值对象。

同样的原则也适用于方法参数：`LocalDate` 类型的参数通常可以可靠地进行标量化，而 `Object` 或 `T` 类型的参数则不行。（不过，如果方法调用能够被内联，JIT 仍然可能完全跳过相关赋值和堆分配。）

影响 JVM 是否能够进行扁平化和标量化的第二个因素，是使用值类的 class 文件内容。一个类在编译时，其字段和方法签名中提到的值类名称会记录在新的 class 文件属性 `LoadableDescriptors` 中。这个属性使 JVM 能够足够早地加载这些值类，从而建立扁平化字段和标量化方法参数。

如果值类 `V` 没有列在 `C.class` 的 `LoadableDescriptors` 属性中，那么 JVM 在加载 `C` 时可能还不知道 `V` 是值类。实际而言，这意味着：如果一个已有的类 `V` 后来被迁移成值类，那么为了获得最佳性能，此前针对旧版 `V` 编译的其他类最好重新编译。

当引用无法进行扁平化或标量化时，JVM 会使用普通引用，指向堆中分配的对象。在非最佳情况下，这可能导致每次读取字段或调用方法时都分配一个新对象。这种情况最常见于程序的预热阶段，也就是 JVM 的 JIT 尚未生成优化代码之前。

## 后续工作

- [JEP 402](https://openjdk.org/jeps/402)，_增强的基本类型装箱（Enhanced Primitive Boxing）_，将改进基本类型的处理方式，使其能够利用装箱为值对象后更轻量的特性。

- [JEP 218](https://openjdk.org/jeps/218)，_支持基本类型的泛型（Generics over Primitive Types）_（经修订），将允许泛型类和泛型方法在使用值类类型作为类型参数时，对字段、数组和局部变量的布局进行特化。

## 替代方案

- 如前文所述，JVM 长期以来都会执行逃逸分析，用来识别那些在整个生命周期内从未依赖身份、因而可以进行标量化的对象。不过，这类优化在一定程度上不可预测，而且对逃出优化作用域的对象无能为力，例如存储在字段或数组中的对象。

- C 语言及其相关语言支持 `struct` 以及类似类抽象的扁平化存储。例如，C# 语言提供了[值类型（value types）](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/value-types)。与本文的值对象不同，这些抽象结构的实例具有身份，这意味着它们支持字段修改等操作。因此，赋值、方法调用等场景中的复制语义都必须谨慎规定，从而带来更复杂的用户模型，也减少了运行时实现的自由度。我们更倾向于本文的方案，把这些底层细节交由 JVM 实现者自行决定。

## 风险与假设

- 这一特性对 Java 对象模型做出了重大修改。开发者可能会对 `==` 运算符和 `synchronized` 关键字的行为变化感到意外，也可能因此遇到 bug。我们预计这类影响会比较少见，而且通常可以处理。

- 某些变化可能影响身份对象的性能。例如，[`if_acmpeq`](https://download.java.net/java/early_access/jdk28/docs/specs/jvms/jvms-6.html#jvms-6.5.if_acmp_cond) 字节码（也就是 `==`）通常只需要一个指令周期，但现在还需要额外检查一次，以判断对象是不是值对象。不过，身份类这一常见情况可以优化成快速路径，我们相信已经把潜在的性能回退控制在最低程度。

- `==` 运算符和 `identityHashCode` 方法可能间接暴露 `private` 字段的值，因此存在安全风险。此外，在比较由大量值对象组成的两棵大型树结构时，`==` 运算符的执行时间没有固定上限。开发者需要理解这些风险。
